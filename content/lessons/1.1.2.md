# Lesson 1.1.2 — Business Scenarios and Use-Case Discovery

**Status:** Authored deep-learning lesson. **Java source:** [Food Ordering Platform commit ed15adb49737a583488e6e2c5ac73158cdf15032](https://github.com/fasiltadesse22/food-ordering-platform-new/tree/ed15adb49737a583488e6e2c5ac73158cdf15032). **Evidence:** Maven CI [run 42512439923](https://github.com/fasiltadesse22/food-ordering-platform-new/actions/runs/42512439923), 13 tests. **Trust boundary:** React simulations are not live Java execution.

## Orient — The business question behind POST /orders

A customer chooses two Lentil Bowls from Cedar Kitchen and sends an order request. The platform returns HTTP 201 Created. What happened? It accepted and recorded an **order-request intake resource**. The restaurant has not accepted any work, and no payment operation has begun. If a product page tells the customer “Your food is confirmed and paid,” the business contract is wrong even though the controller returned a technically valid response.

This lesson asks: **Which end-to-end business outcomes must the platform support first, and how do we specify, implement and verify the first outcome correctly?** Success must be defined in the language of the actor's goal and an observable system postcondition, not inferred from green HTTP status. The Food Ordering Platform now implements one genuine vertical slice in Java: validate a requested basket against a fictional server-owned menu, create an intake ID and quotation, store it in volatile process memory, and return the precise pending-restaurant/no-payment status.

Why begin so narrowly? Lesson 1.1.1 identified different actors and sources of authority: customer intent, merchant fulfillment, payment-provider financial outcome, and platform communication. The first executable workflow must respect those boundaries instead of implementing a single misleading “order successful” flag. This is still meaningful project evolution: a real request passes through Spring MVC, application rules, a domain record, a storage adapter and a retrievable HTTP resource.

**Prediction:** A customer sees 201 and the restaurant never accepts. Is the backend necessarily broken? Not under this explicit contract. The missing merchant decision is a separate business capability. An incorrect UI promise could be broken, or the product could be incomplete, but the initial intake might have behaved exactly as specified.

This lesson combines deep use-case analysis with actual Java tests, source-linked execution tracing, and synthetic future scenarios. It does not implement restaurant acceptance, live payments, refunds, delivery or production durability. You will learn to distinguish documented behavior, illustrative modeling, measured evidence and missing guarantees at every step.

## Understand — Capabilities, use cases, user stories and endpoints

A **business capability** is a stable ability an organization must provide, such as managing customer intent, coordinating fulfillment or resolving payment disputes. Capabilities survive changes in deployment topology and teams. A **use case** describes an actor pursuing a goal through an interaction with an observable outcome, including rejection and alternate paths. A **user story** captures desired value at planning level, but is not enough to define a precise execution contract. An **endpoint** is only one technical entry mechanism.

Consider the story: “As a customer, I want to submit my selected meal so that the restaurant can consider it.” That story does not tell us whether POST /api/orders only records intent, whether it waits for merchant confirmation, when a card might be charged, or what rejection means. The use-case specification must explicitly supply those answers. Likewise, a REST endpoint named PlaceOrder does not acquire the ability to make a restaurant accept by virtue of its URL.

We distinguish **four propositions**: customer requested purchase; platform recorded the request; restaurant accepted fulfillment; provider confirmed its financial operation. Each has different authority and evidence. The initial Java code proves only the second (given appropriate input) and records the first as a supplied intent. There is no merchant or provider network call.

A use case's **primary actor** initiates the desired result; supporting actors contribute without owning the same decision. A stakeholder may care about the outcome but never interact with the API. The software boundary is chosen after these roles are clear. Asking “Which microservice should own PlaceOrder?” before defining its postcondition reverses the reasoning chain.

**Worked example:** Customer requests two bowls; a synthetic catalog says the menu entries are available; the platform records an intake. None of those steps establishes restaurant kitchen capacity at the moment of preparation. If the product requires immediate merchant confirmation, then our use-case boundary and implementation must change; renaming a method is not a substitute for negotiating a new business promise.

## Understand — Formal UC-001 structure and its main flow

**UC-001 Submit Order Request.** Primary actor: customer. Trigger: HTTP POST /api/orders. Preconditions: caller supplies a UUID-like customerId, a known demo restaurant code, and 1–20 distinct menu codes with quantities 1–20. The supplied customer UUID is **not authenticated**; this is a demonstration contract, not a production identity system. The synthetic Cedar Kitchen catalog is a server-side fixture and not a connected merchant inventory feed.

**Normal flow:** (1) OrderController parses JSON and performs structural validation. (2) It translates request fields to PlaceOrderCommand without a client-supplied price. (3) PlaceOrderService resolves the restaurant fixture through MenuCatalog. (4) Business checks reject unknown restaurant, unknown or unavailable item, duplicated item line and invalid quantity. (5) It computes a synthetic quoted total in integer cents. (6) It creates an immutable Order intake record with ID, timestamp, customer reference, restaurant reference, and line snapshots. (7) It stores the record through OrderRepository, whose initial implementation is a process-local ConcurrentHashMap. (8) The controller returns 201 Created, Location, an explicit intake status and independent merchant/payment fields.

**Observable success postcondition:** the process has a retrievable intake resource while it remains running. **Not promised:** restaurant accepted the order; payment authorized, captured or settled; kitchen preparation started; data survives restart; duplicated requests produce one effect.

Why 201 rather than 202? Because the API creates an addressable intake resource immediately. Pending *merchant fulfillment* is a different proposition from creation of that resource. A 202 could be defensible in an alternative processing contract, but the decision must follow observable semantics, not the blanket claim that any pending downstream business step makes 201 inappropriate.

The API response is explicit: intakeStatus REQUESTED_AWAITING_RESTAURANT, restaurantDecision PENDING, paymentStatus NOT_STARTED. The meaning field clarifies what happened. A GET on Location retrieves this particular intake while the process lives. A valid HTTP status plus these facts constitutes a narrow, testable business acceptance criterion rather than a misleading end-to-end success claim.

## Understand — Preconditions, policy guards and postconditions

Separate **structural input validation** from **business-context decisions**. A missing customerId or quantity zero violates the JSON input contract and produces HTTP 400. A syntactically valid item code that is not listed for Cedar Kitchen, or a listed seasonal item marked unavailable, violates the teaching catalog business rule and produces HTTP 422. An HTTP adapter can validate shape; an application use case must decide whether the requested operation is permitted by current business policy.

A **trigger** initiates the interaction. A **precondition** identifies facts that must hold before success. A **guard** evaluates permission to proceed. A **postcondition** is an observable fact promised after the operation. In this lesson the guards are modest: known demo restaurant, available requested items, valid distinct lines. Later lessons explore fuller state machines, atomic guards and concurrency.

The testable fact is not “order completed.” It is “the platform has recorded an order request in local volatile storage.” A merchant capacity decision remains external, and the financial operation has not been initiated. This separation matters because clients might incorrectly treat an intake acknowledgement as permission to dispatch a courier or capture funds.

Suppose a payload is syntactically valid and references seasonal-special. The JSON validation succeeds, but the catalog fixture marks it unavailable. The application rejects 422 ITEM_UNAVAILABLE. Suppose quantity is zero: input validation rejects 400 INVALID_REQUEST. Both are expected responses, not infrastructure outages. Reporting both as 500 would erase the distinction and mislead clients about whether retrying is useful.

A complete use-case discovery process records rejected outcomes and their implications before coding. It also records which authority supplies each fact. Here the server fixture owns demonstration price and availability values; it does **not** attest to live merchant capacity or a real commercial offer. True business policy needs stakeholder approval, which a passing unit test cannot provide.

## Understand — Alternative flows, errors and ambiguous outcomes

Use-case discovery is incomplete without alternatives. The implemented negative paths include malformed JSON, empty basket, quantity outside 1–20, unknown restaurant, unknown menu item, unavailable item and duplicate menu-item lines. The first category is rejected at the HTTP validation boundary with 400 INVALID_REQUEST. The remaining business rejections normally return 422 with a specific code. GET of a missing intake returns 404.

These codes have different meanings. 400 tells a client its input contract was invalid. 422 says the request representation may be valid but an application rule disallows it. A 201 means the intake resource was created. A 404 on a subsequent GET means this *process* cannot currently find that ID; it does not prove the resource never existed, since a restart erases in-memory storage.

An unexpected infrastructure error is different from an expected business rejection. If a response is lost after the platform records an intake, the client may not know whether it committed. Blind retry could create a second intake record: the current application is explicitly **not idempotent**. A diagnostic X-Request-ID header helps link logs; it is not an exactly-once or deduplication mechanism. This is a legitimate baseline risk to address in later lessons.

Future alternatives include a restaurant rejecting after intake, a provider declining after acceptance, and a customer canceling after kitchen work begins. These are different use cases involving authority, terminality, compensation and policy. The academy should map them conceptually, but it would be false to show them as executed by this Java baseline.

When diagnosing a 2xx response followed by an unfulfilled meal, first ask which business step succeeded. A queue, a retry or a circuit breaker cannot repair a missing business decision right. By recording alternate flows and their causes, we can later select architecture mechanisms for specific observed failure windows rather than inventing them prematurely.

## Understand — Identity, price provenance and durability boundaries

The first slice uses a caller-provided customer UUID, a static restaurant code and a generated order-request UUID. Those are **different identities**. The customer UUID is not authentication or authorization; anyone able to access this demo endpoint could supply another UUID. The restaurant code identifies a fictional menu fixture. The order ID identifies one recorded instance of intent, not necessarily a unique customer purchase across retries.

Prices come from the server fixture. The client sends menu item codes and quantities but cannot provide unit price. This reduces one trivial trust error, yet does not solve production pricing: there are no merchant contracts, discounts, tax policies, price-lock durations, promotions, currency conversion or real inventory freshness guarantees. QuotedTotalCents for two Lentil Bowls is 2500 synthetic USD minor units. It is not a settled or charged amount.

The repository is intentionally a ConcurrentHashMap. It is sufficient for a simple runnable baseline and isolated tests, but loses data when the process restarts. Concurrency-safe map operations do not prove all future business invariants are atomic, and one instance does not share state with another. Real durability, optimistic concurrency, persistence transactions and distributed consistency will be introduced only when motivated by a concrete requirement and evidence.

Two identical POSTs currently create two different intake records. This is documented in the application tests. An identical JSON body might represent either duplicate delivery of one intent or two genuine separate orders; deciding the semantics requires a later idempotency contract. A request correlation ID helps debugging but cannot decide business equivalence.

**Engineering discipline:** maintain a ledger with implemented result, observed test, non-guarantees and revisit trigger. This prevents downstream features from relying on assumptions the current slice never satisfied.

## Explore — Derive a use case from actor and outcome

Use the interactive Use-Case Explorer to change the actor and objective. Compare Customer → Submit order-request intake (implemented) with Restaurant → Accept fulfillment (not implemented), Provider → Confirm a financial operation (not implemented) and Support → Approve remediation request (unresolved policy and not implemented). Inspect each actor's trigger, preconditions, decision owner, normal flow, rejection, postcondition and evidence source.

When an actor's goal changes, the system boundary changes. A restaurant has authority to decide feasibility; the platform's fixture can only reject a basket based on synthetic data. A payment provider owns actual authorization/capture/refund outcomes; an Order controller cannot create those facts by setting a local flag. A support agent may request a refund within policy, but the provider confirms completion.

Try rewriting the product promise as “Order is confirmed only after the restaurant accepts.” The present use case cannot fulfill it. You must add a genuine merchant decision interaction or change the customer-facing promise. A status-code rename does not create authority. Compare a smaller scope that is fully true against a larger scope that lacks business evidence.

The project is not expected to simulate every actor to look impressive. It is expected to make the implemented and deferred boundaries legible, so later lessons can introduce those capabilities when they are actually earned.

## Predict — Derive acceptance criteria and tests

A good acceptance criterion is a falsifiable statement about an observable business result. It names **Given** conditions, **When** trigger, **Then** exact expected response or state. It should also identify how the result is verified and which adjacent guarantees are not covered.

AC-01: known restaurant and available item → 201 Created, Location, order ID, quotedTotalCents 2500 for two bowls, restaurant PENDING, payment NOT_STARTED. AC-02: GET on the returned Location → 200 with same intake state while the process remains alive. AC-03: malformed JSON or quantity zero → 400 INVALID_REQUEST. AC-04: unavailable item or unknown restaurant → 422 with a business-specific code. AC-05: repeated identical POST → distinct order IDs (an explicitly undesirable safety limitation, not a promised exactly-once effect). AC-06: quote derives from server fixture rather than client-supplied price. AC-07: absent ID read → 404.

In the Acceptance Explorer select a case, predict the status or business outcome, then reveal the Given/When/Then path, request/response example, named Java test, exact source file and CI evidence. Distinguish the **testable result** from untested future claims. No test can prove a restaurant accepted this order because there is no acceptance capability in the implemented code.

The most valuable question to ask after a test passes is: “Which business expectation could still be false?” A successful 201 does not prove a meal will be made. A passing map persistence test does not prove restart durability. A structural validation test does not prove authenticated identity. This questioning creates the quality-attribute forces needed for later architecture work.

## Engineer — Source-linked execution and architecture decisions

The real project is one Java 21 / Spring Boot 4.1 deployable. The trace begins at OrderController, which parses and validates the HTTP payload and translates it to PlaceOrderCommand. PlaceOrderService uses MenuCatalog to check the synthetic merchant fixture, validates the basket, computes server-owned cents and creates immutable Order data. It writes via OrderRepository, backed initially by InMemoryOrderRepository. OrderController maps the result to an HTTP resource and expresses the exact pending status.

This design separates *HTTP concerns* from *business decision logic* and *local storage mechanics*. The service can be tested directly without HTTP. The repository port has a present purpose: testability and later replacement of the volatile adapter. It is not an excuse to create a general abstract repository framework. The catalog port similarly preserves the boundary between request intent and fixture-controlled values.

Why not create OrderService, RestaurantService and PaymentService as separate deployments? This first business use case requires no remote collaboration. A premature split would add request timeouts, partial failures and operational obligations without making merchant authority or payment semantics more correct. **Single deployable** is a valid and reversible starting decision, recorded in an ADR with explicit reconsideration triggers.

The interactive Execution Trace links each visible step to the **exact Java source at an immutable commit**. It is a source-derived visualization; we did not instrument a production OpenTelemetry trace. The CI-linked integration test is evidence that selected real framework behavior executed, which has a different epistemic status.

The deliberate project evolution outcome is a runnable, independently verified baseline. Future clusters can first reproduce fragile behavior and then show why a mechanism becomes necessary. We should never claim a different architecture was needed merely because it appears later in the curriculum.

## Diagnose — 201 but the restaurant never accepted

An incident report says: “The order API succeeded but the restaurant never accepted it.” Generate competing hypotheses before adding a retry queue. First: a **semantic misunderstanding**—201 meant the platform recorded an intake, not restaurant confirmation. Second: a **UI contract error**—the user-facing screen incorrectly says “confirmed.” Third: an **ephemeral storage limitation**—a process restart erased the record, so a subsequent GET returned 404. Fourth: a **missing integration**—the product requires merchant review, but no merchant notification or decision use case was ever built. Fifth: an **ambiguous retry**—two POSTs produced separate intake IDs.

Inspect the actual API response fields. The backend explicitly says merchant PENDING, payment NOT_STARTED. This supports the first explanation and excludes the false conclusion that 201 automatically meant restaurant acceptance. Check the returned Location and GET within the process lifetime. Inspect correlation headers and logs, without mistaking them for proof of customer identity or idempotency. Verify whether an actual merchant integration exists before searching for network failures.

The Diagnosis Room lets you select evidence and a provisional hypothesis. Its clues are synthetic exercises; they are not real production telemetry. A strong report states symptom, promised postcondition, evidence, alternative causes, discriminating next test, mitigation and what is still unknown.

**Architecture critique:** returning 202 instead of 201 does not create a restaurant approval mechanism. A different status code is justified only by a different resource/processing contract. Accurate business semantics come first; implementation mechanisms follow.

## Defend — Staff review and audience adaptation

For a backend colleague: “POST /api/orders validates a customer-supplied basket, checks a static server-side fixture catalog, creates a local intake record through a repository port, and returns 201 with merchant PENDING and payment NOT_STARTED. The use-case logic is testable without HTTP.”

For a Staff reviewer: “We selected a single deployable because the measured force is truthful intake semantics, not distributed release cadence or independent scaling. The ADR records alternatives and fragilities: volatile storage, unauthenticated caller IDs, non-idempotent POST and no external authority integration. We will revisit topology when a real business requirement or reproducible failure justifies it.”

For a stakeholder: “We can record the meal you requested. We cannot yet promise the restaurant agreed or that a card was charged. Before real use, we need merchant confirmation, authentic customer identity, commercial pricing and payment-policy decisions.”

Adversarial questions: Does HTTP 201 guarantee full business success? No. Is an X-Request-ID a deduplication key? No. Does a fixture price make commerce secure? No. Are microservices mandatory because the curriculum teaches them? No. Could a 201 coexist with future merchant rejection? Yes, if it is explicitly an intake contract.

The answer is a reasoning chain, not a pattern catalog: **business capability → actor goal → use-case contract → alternatives → tests → implementation → evidence → non-guarantees → next forces**.
