# Lesson 1.1.3 — Commands, Decisions, Facts and Events

**Cluster 1.1 · Chapter 1 · Type A: verified Java application evolution and React visual textbook**

**Engineering question:** What separates an intention to change state from proof that it changed?

**Prior knowledge:** Lesson 1.1.1 established business actors, capabilities and authority; Lesson 1.1.2 established UC-001, the truthful intake contract and the first runnable Java baseline. This lesson builds on both without inventing merchant acceptance, financial operations or distributed messaging.

**Source-of-truth rule:** An authored diagram is an explanation. A browser scenario is a deterministic educational model. A Java test is executed evidence under test conditions. A stored resource is not automatically a durable business transaction, and a provider outcome belongs to the provider's authority.

## Orient — A customer request is not a historical fact

Imagine a customer presses **Place order** twice because the first screen spins. The platform logs a request, the second response returns HTTP 201 Created, the restaurant has seen neither request, and the customer asks whether money was charged. Four statements now sound similar but have entirely different evidentiary foundations: the customer **wanted** an order, the platform **decided** whether to record an intake, the current process **contains** an intake record, and the external payment provider **might or might not** have processed a separate operation. In today's application, that last operation was never initiated.

A platform that collapses all four into one optimistic status will be hard to operate even if its HTTP requests and unit tests are green. A better model names each transition in meaning, not in API nomenclature. A command is the request to perform an operation. A decision determines whether the request is permitted. An established local fact describes an effect that can be observed within the relevant storage scope. An event is a representation of a claim about that historical fact. An acknowledgement tells a caller something about processing; its wording and arrival are separate from what really happened.

The crucial direction of implication is **not reversible**. A valid PlaceOrder command does not imply an Order was recorded. A recorded order request does not imply restaurant acceptance. A log line announcing intake does not prove that a durable database committed. An HTTP timeout does not prove the request was rejected or absent. Each inference needs its own evidence and authority.

### The concrete baseline

The current Java application is one Spring Boot process. OrderController translates an HTTP POST into PlaceOrderCommand. PlaceOrderService checks a fictional server-owned restaurant menu, constructs an immutable Order request-intake record and calls a process-local ConcurrentHashMap repository. A successful POST creates an intake resource and returns **201 Created** with Location, intakeStatus **REQUESTED_AWAITING_RESTAURANT**, restaurantDecision **PENDING** and paymentStatus **NOT_STARTED**. Nothing calls a merchant or payment provider. Storage disappears on process restart. Repeating a POST creates a new UUID and a second intake.

**The lesson's job is to improve this truth model without changing what UC-001 actually promises.** We will introduce an explicit local decision outcome and an appropriately named **OrderRequestRecorded** fact, and demonstrate why neither is proof of anything beyond a normally returned in-process save.

### Questions to hold while studying

1. Exactly what did the customer ask us to do, and what was never requested?
2. Which actor or component has the authority to decide whether this particular operation is allowed?
3. Which observation distinguishes a successful local state change from a plausible story about that change?
4. If the response disappears, what can the caller infer about the stored state?
5. What would have to change before **accepted**, **paid**, **refunded** or **durably committed** became defensible labels?

## Understand — Commands express intention, not completed state

A **command** requests a particular business behavior. PlaceOrder asks the platform to register customer intent under defined rules. AcceptOrder would ask an authorized restaurant actor to make a fulfillment decision. RequestRefund would ask a qualified authority to initiate a financial remediation process. These verb-oriented names describe intent and desired action, not outcomes that have already occurred. The appropriate past-tense fact for this platform's implemented operation is **OrderRequestRecorded**, not the ambiguous OrderPlaced and certainly not OrderAccepted.

A command has a caller, a target, a business purpose, operands, and constraints. The current PlaceOrderCommand contains customerId, restaurantId and a list of item codes and quantities. The supplied customer UUID is an identity **claim**, not authenticated user authority. The restaurant code identifies the target fictional menu, not a live merchant connection. The line quantities describe requested basket contents, not inventory reservations. The synthetic price is deliberately not supplied by the caller.

Different representations exist at different layers:

| Layer | Example | Responsibility | What it does not prove |
|---|---|---|---|
| HTTP transport request | POST /api/orders with JSON | Parse syntax, map fields, set transport contract | Caller identity or business approval |
| Application command | PlaceOrderCommand | Express requested business behavior | Validity, acceptance, or execution |
| Business decision | Recorded or Rejected | Apply actual business rules | Crash durability or external fulfillment |
| Domain record | Order request intake | Represent accepted local request state | Merchant approval, payment or fulfillment |
| Local historical claim | OrderRequestRecorded | Describe save that returned normally | Distributed commit, broker delivery or consumer receipt |
| HTTP acknowledgement | 201 + Location | Tell caller an intake resource was created | That caller received the response or restaurant accepted |

### Valid shape is not valid authority

A well-formed JSON document can still be prohibited. HTTP structural validation checks a UUID shape, nonempty restaurant ID and valid quantity bounds; the application checks whether a fixture restaurant exists and whether an item is present and available. Neither the presence of a customer UUID nor a syntactically correct restaurant ID authenticates the actor. An authorization gate would be an independent prerequisite for real users. We must not hide that missing gate under the word validation.

The concept of an **expected state** belongs to commands that operate on an existing business identity: for example, a future AcceptOrder command might name an OrderId, merchant identity, expected version and a reason, then be rejected when the order is already cancelled. The current PlaceOrder creates a new local intake, so there is no preexisting Order version to enforce. Adding an expected version field today without a real target state would not improve correctness.

### Command acceptance has at least three meanings

**Received** means a transport adapter has bytes. **Accepted for evaluation** means syntax and initial entry requirements permitted application processing. **Business operation completed** means the responsible service successfully established its promised postcondition. A system might acknowledge only reception (202 Accepted), or create a resource (201 Created), or report a rejection (4xx). None of those status codes supplies a broader business guarantee by itself. The actual response body and use-case contract must say what was done.

This distinction matters operationally. If a customer sees 201 but the restaurant later declines, the original 201 may have been correct for intake. If the UI instead promised “Your dinner is confirmed,” the defect is likely in the business contract or presentation of that contract, not necessarily in request processing.

## Understand — Design command contracts around business ownership

A command contract is not merely a Java record with fields. It names the operation and its preconditions, authority, expected outcome, known rejections and effect scope. It must specify which facts can be established by the receiving application and which require someone else.

For UC-001 the application can determine if a synthetic menu item is marked available and can record request intake. It cannot authenticate the identity of a real customer, ask a real restaurant to accept food preparation or certify provider payment. Those are missing business operations and authority integrations, not simply missing booleans.

### Required and optional command information

- **Business intention:** PlaceOrder, rather than SetOrderStatusToPlaced; the caller requests work and the domain decides its state.
- **Initiator and claimed identity:** the supplied customer reference, explicitly unauthenticated in this teaching baseline.
- **Target:** a restaurant fixture and selected menu lines; a future state-changing command may target an existing OrderId.
- **Constraints and expected state:** quantity limits and menu availability now; an expected state/version only when modifying a real existing entity.
- **Correlation information:** X-Request-ID can support tracing; it is not a business operation ID, uniqueness guarantee or idempotency protocol.
- **Decision and result contract:** either record a new intake resource or explain why this attempt was rejected.
- **Effect boundaries:** only local process memory and the returned request resource; no real financial or restaurant side effects.

Do not add fields just to make a DTO appear enterprise-grade. For instance, an arbitrary idempotencyKey string with no durable uniqueness constraint and no atomic deduplication would create a dangerous false confidence. Similarly, an asserted merchantId does not become authorization proof until a real identity and policy mechanism exists.

### An architectural counterexample

Suppose a developer writes a controller that accepts a request and immediately returns success, while a worker later checks the basket. This might be a valid asynchronous-intake design if the status clearly means **request queued**, the queue actually exists, and later failure is observable. It is not valid to label that response **order confirmed** without a merchant decision. The command shape can be identical in both designs; only the execution and postcondition contract differentiate them.

In a second design, the controller calls the current synchronous application service, which saves intake and returns 201. That response may truthfully claim **local resource created**, but it cannot claim restart durability. Business semantics must be attached to the operation's actual effect, not copied from fashionable HTTP or messaging conventions.

## Understand — A decision is an outcome, including a principled rejection

Once a command reaches the application, the system evaluates the business conditions that actually belong to its authority. For PlaceOrder, the fixture restaurant must exist; the basket needs one to twenty distinct items with permitted quantities; every item must be known and available; arithmetic must stay within supported bounds. Passing a guard is a local policy decision, not a restaurant's decision to prepare a meal.

The prior Java service already threw BusinessRejection for predictable invalid business input. Lesson 1.1.3 makes the distinction explicit in a typed internal outcome: **PlaceOrderOutcome.Recorded(order, fact)** or **PlaceOrderOutcome.Rejected(code, message)**. The original place(command) method still returns the Order or throws a BusinessRejection, so existing HTTP responses remain backwards compatible.

| Situation | Decision classification | Successful OrderRequestRecorded? | HTTP meaning |
|---|---|---|---|
| Known available fixture item, save returns normally | Recorded | Yes, local in-process claim | 201 created local intake |
| Unavailable fixture item | Business Rejected | No | 422 ITEM_UNAVAILABLE |
| Unknown restaurant fixture | Business Rejected | No | 422 RESTAURANT_NOT_FOUND |
| Duplicate menu line | Business Rejected | No | 422 DUPLICATE_ITEM |
| Malformed HTTP input | Transport rejection before command | No | 400 INVALID_REQUEST |
| Repository saves then throws | Infrastructure/unknown effect | No fact returned; data may exist | Do not claim a normal business rejection |
| Second identical POST | A second independent command | Yes, another local fact | Another 201, different resource identity |

### Rejection is not a success event

A rejected command may be an interesting observation. A troubleshooting system could record **OrderRequestRejected** as an attempt or audit message, but that is not an **OrderRequestRecorded** success fact. Negative business decisions can themselves be described as facts if they are recorded in an appropriately scoped ledger; their semantics must remain negative and separate. Our Java application currently returns a typed rejection and does **not** implement a persistent rejection history.

A common anti-pattern is constructing OrderPlaced before checking business guards because an event is used as a generic “something happened” log. If validation later fails, consumers might observe a success-shaped claim for a rejected operation. Name events by completed facts and create them at a justified effect boundary.

### Infrastructure errors are not ordinary rejections

A backend can fail after beginning a side effect. A storage adapter could write the Order then throw an exception while returning. If our handler converted every exception into Rejected, a caller would confidently infer no state change even though the record might exist. The new Java handler catches **only the expected BusinessRejection** and allows unexpected storage exceptions to propagate. It returns no successful fact in that exceptional case; it also does not assert the record was absent. That is a deliberate, conservative limit.

## Understand — Domain facts, events, logs and messages are distinct

A **business fact** is a proposition about something that has actually occurred in a defined business context: for example, a platform created an order-request intake resource. A **domain event** describes a relevant state transition or decision as historical meaning; its name usually reads in the past tense. A **log entry** is an observation emitted for troubleshooting. An **integration event** is a message representing a fact for other components, with its own publishing and delivery conditions. These concepts overlap in content but differ in purpose, scope and what evidence supports them.

In the current implementation, **OrderRequestRecorded** is a small immutable value returned from the command handler only after the process-local repository's save returns normally. It includes the intake order ID, customer reference, restaurant reference, creation time and local observation time. It is not written to a durable event store, published to a broker, available through a new HTTP endpoint, or guaranteed to survive a crash. Its very existence on the success path is useful for modeling but cannot strengthen the storage adapter's promises.

### Why names matter

The blueprint uses the illustrative sequence **PlaceOrder → decision → OrderPlaced**. In some products, “placed” means merely that a request was submitted; in others it means that a restaurant accepted work or payment authorization succeeded. The name alone is dangerously ambiguous. For this real Java milestone, the specific name **OrderRequestRecorded** commits to a narrower and falsifiable proposition.

Likewise, **AcceptOrder → OrderAccepted** belongs to an actual restaurant decision workflow, which does not yet exist as an authorized Java operation. A future payment provider may confirm **PaymentAuthorized** or **PaymentCaptured**, but those outcomes require real provider evidence. The platform must not mint a settled financial fact merely because its local code tried to send a request.

### Event generation, recording, publishing and observation

Distinguish four steps before claiming “we have an event”:

1. **Construct a value** that describes what the domain believes happened.
2. **Establish the underlying state effect** within the actual local storage semantics.
3. **Record or publish the event** through a defined channel, if the architecture requires that.
4. **Verify consumer observation or effect**, if a downstream guarantee is promised.

A Java object in memory satisfies only a limited part of this chain. An application log line does not make an external subscriber receive a message. A broker acknowledgement might prove publication to a particular broker under a stated condition, yet not prove that an inventory or payment side effect completed. Event Sourcing is a separate storage architecture in which events are the authoritative record; it is not implied by using event-named records.

**Do not confuse fact creation time, storage commit time, producer acknowledgement time or consumer observation time.** The current Order.createdAt is set before save; OrderRequestRecorded.observedAfterSaveAt is taken after save returns. Neither is a durable database commit timestamp, and the clock can be fixed in tests. An ordered pair of timestamps is not itself evidence of an atomic transaction.



## Understand — Acknowledgement is a separate claim about execution

The platform can do work and still fail to tell the caller what occurred. Acknowledgement is communication, not the historical fact itself. This becomes especially important when retries are involved and when a user interface reduces a nuanced response to a single success badge.

For the implemented UC-001, **201 Created** means the platform created a local order-request resource in its current process and returned a Location that can be queried while that process remains alive. It does **not** say the restaurant accepted fulfillment, that payment was authorized or that the order is crash-durable. The customer might not receive that response because a connection closed or a proxy timed out after the server performed its work. The application's result and the client's observation are then different.

### Four acknowledgements that should never be merged

| Level | Truthful statement | What it cannot independently establish |
|---|---|---|
| Transport reception | HTTP request reached a server | Business rules passed or work completed |
| Application decision | Service evaluated command and returned Recorded or Rejected | Durable persistence, external effects, client receipt |
| Storage adapter normal return | In-process save method returned without exception | Survival of process crash, replication or another machine's observation |
| Remote/provider acknowledgement | A named external authority attested to a specific operation | Unrelated business effects or settlement beyond that authority's contract |

The **customer-facing acknowledgement** is yet another presentation layer. A React page that says “Order confirmed” after a 201 intake response is inventing a merchant promise. A truthful screen could say “We recorded your request; the restaurant has not accepted it yet.” This distinction is not wordsmithing: it changes support expectations, recovery behavior and what the company may claim to have delivered.

### Side-effect intention versus confirmed effect

Suppose a future refund operation is designed as **RequestRefund**. That may cause the platform to prepare a request to a payment provider; its own local fact might be **RefundRequestRecorded**, not **RefundCompleted**. The provider's authoritative receipt is needed before claiming successful refund execution. Even a provider's accepted-for-processing acknowledgement may not be settlement. Until that contract is implemented and verified, the academy must label the complete scenario **conceptual**.

The same pattern applies to merchant acceptance. A platform message *asking* a restaurant to accept is not an acceptance. A scheduled kitchen task is not a completed meal. Side-effect intent, remote acknowledgement, and authoritative completion each occupy a different boundary.

## Understand — Failure windows and the uncertainty timeline

Consider the following source-derived local sequence for a valid PlaceOrder request. The numbered order matters because it determines which conclusions can be safely drawn when execution stops.

1. **Request received:** an HTTP POST arrives; no business condition has yet been evaluated.
2. **Command created:** OrderController maps fields into PlaceOrderCommand; this is still intent.
3. **Business checks performed:** PlaceOrderService resolves the fictional restaurant, validates items and computes a synthetic total.
4. **Record constructed:** immutable Order is created with a fresh UUID and createdAt; merely having this value does not prove storage.
5. **Save attempted:** OrderRepository.save(order) is invoked against process-local memory.
6. **Save returned normally:** the application can observe its local adapter's normal return.
7. **Local fact returned:** the new handler constructs OrderRequestRecorded and returns Recorded(order, fact) to its caller. The legacy place() adapter exposes the Order to the controller.
8. **HTTP response written:** controller attempts 201 Created, Location and pending/no-payment fields.
9. **Client observes response:** only now can that specific client know what the server told it; even the response's words must remain scoped.

A failure at stage 3 is a known business rejection before storage. A failure at stage 5 can be genuinely ambiguous: the adapter could mutate state then throw. A failure at stage 8 may occur even after a normal local save and after the fact was constructed. The client must not infer that the order does not exist simply because the acknowledgement was never delivered. Stage 9 is a transport observation, not a proof of permanent storage.

### Two indistinguishable client observations

**Case A: rejected or lost before processing.** The client sends PlaceOrder and receives a timeout. The server did not store the record.

**Case B: recorded but acknowledgement lost.** The client sends the identical PlaceOrder and receives the same timeout. The server stored intake successfully; the response was dropped.

From the client's viewpoint these cases are identical. Retrying without a stable business-operation identity can either fulfill the original intent or create a duplicate. The correct operational response requires some authoritative lookup or an explicitly engineered idempotency/reconciliation protocol—not a guess based on HTTP failure.

### A third case: write then throw

The new Java tests inject a repository that appends an Order to its in-memory list and then throws an IllegalStateException. The handler propagates that infrastructure error and returns **no** typed Recorded outcome. Yet the test's repository contains the new Order. This proves an important negative point about our chosen boundary: **absence of a returned success fact is not proof of absent state** when infrastructure execution becomes uncertain.

The test is deliberately an isolated failure-model experiment. It does not claim that the current ConcurrentHashMap always exhibits this exact failure. It shows why a generic catch-all handler that turns every thrown exception into Business Rejected would be unsafe.

### State consistency and time semantics

Two independent in-memory collections—one for orders and another for events—would create another dangerous partial-state window. Without a shared atomic transaction, the application could save an order but fail to append an event, or append an event for an order that later fails. This lesson therefore does **not** add an independent event journal. OrderRequestRecorded is returned as a local descriptive value only after a normal save. This intentionally does not solve durable event recording or exactly-once external delivery.

Later lessons about state, concurrency, transactions and reliability may justify stronger mechanisms. They must be motivated by a clear business invariant and actual failure observations, not installed as a default technology stack.

## Understand — Duplicate requests, correlation and idempotency

The current application has no idempotency guarantee. A valid PlaceOrder command generates a fresh intake UUID on each execution. Two identical HTTP POSTs therefore produce two distinct records, each with its own local OrderRequestRecorded fact. The tests explicitly assert this behavior; it is a **known limitation**, not a hidden implementation defect.

Distinguish four identities carefully:

| Identifier | Identifies | What it does not do |
|---|---|---|
| HTTP correlation ID | Related log statements or tracing context | Establish business uniqueness |
| Customer UUID | Supplied customer reference in request | Authenticate the caller or deduplicate operations |
| OrderId | One created intake resource | Group every duplicate request for the same human intent |
| Future idempotency key | A stable caller-defined operation identity, only if enforced | Guarantee safety unless uniqueness, expiry, concurrency and result replay are correctly designed |

An idempotency key is **not** merely a field in a command. A correct protocol needs an authoritative place to store operation identity and result, a defined time window, concurrency rules, handling of ambiguous saves, conflict behavior for the same key and different payloads, and a replay contract. Those prerequisites are not present in the current volatile application and belong to future design work.

### Delivery guarantees are conditional

**At-most-once handling** can avoid repeating an operation but may lose work when failures interrupt delivery. **At-least-once delivery** can retry until a receiver observes work but can duplicate effects unless the handler is safe to repeat. **Effectively-once business effect** is usually a composite guarantee under a particular identity, storage and deduplication model, not a magic network-delivery property. A retry policy without corresponding effect protection may increase duplicates.

Do not confuse the number of received messages with the number of business operations actually recorded. A single user action can trigger several network attempts; a second deliberate user action might happen to have the same payload. Distinguishing retry from new intent is a business/API problem as well as an infrastructure problem.

### Worked duplicate timeline

At 12:00:00 the customer submits basket A. The server records intake OrderId O-1 and tries to respond, but the response disappears. At 12:00:03 the client retries the same JSON with the same X-Request-ID. The current server **does not deduplicate**: it records OrderId O-2 and returns another 201. The customer may now see one acknowledgement but two local records. No merchant or payment operation occurred in this application, so the duplication applies to **intake resources** only; we must not invent duplicate charges.

A future system might use a durable idempotency key and stored result to return O-1 on retry. That would require explicit persisted uniqueness and concurrency controls. It must also distinguish a replay from a distinct deliberate order. The blueprint intentionally introduces those concepts now while reserving robust implementation for later prerequisite lessons.

## Understand — Different actors own different facts

A distributed business process is not a single authoritative state machine with one universal truth owner. The Order, Restaurant and Payment participants may agree on the customer journey while owning different decisions and evidence. Distinguish who **requests**, who **decides**, who **records**, who **confirms**, and who **observes**.

| Business proposition | Requester | Decision/fact authority | Current Java status |
|---|---|---|---|
| Customer submits order-request intake | Customer (unauthenticated UUID in demo) | Platform validates and records local intake | **Implemented** |
| Restaurant accepts fulfillment | Platform can request review | Authorized restaurant/merchant decision | **Conceptual only** |
| Restaurant rejects before payment capture | Merchant decides feasibility | Restaurant for fulfillment; provider for any actual money operation | **Conceptual only** |
| Card authorization or capture | Authorized checkout workflow | Payment provider and its confirmed operation | **Not implemented** |
| Customer asks for cancellation | Customer | Policy-defined merchant/platform authority | **Unresolved/Not implemented** |
| Refund request accepted for processing | Customer/platform policy | Platform or merchant policy gate | **Not implemented** |
| Refund completed | Separate provider operation | Provider evidence of financial action | **Not implemented** |
| Kitchen began preparation | Restaurant staff/process | Merchant operational system | **Not implemented** |

### Three stories that sound alike but are not

**“Refund requested.”** Someone expressed intent and perhaps the platform acknowledged receipt. No money can be claimed returned.

**“Refund approved.”** A legitimate authority decided eligibility. That still does not mean the provider performed the refund.

**“Refund completed.”** The financial operation has an authoritative provider outcome. The platform needs to correlate this evidence to the actual requested operation; a successful local HTTP call alone may not be sufficient under the provider's contract.

Likewise, **“Restaurant rejected the order request”** could be a real rejection fact only if an authorized restaurant decision has been observed. Our current fixture's ITEM_UNAVAILABLE rejection is a **local application decision about static demo menu data**, not a live merchant rejection. The domain labels must continue to reveal that distinction.

### Why not implement AcceptOrder now?

The curriculum's illustrative AcceptOrder → decision → OrderAccepted sequence requires an authorized actor, merchant capacity rules, order identity and legal state transitions, guard conditions, cancellation interaction, and a policy for partial or late acceptance. Those contracts are not established by adding a REST endpoint and boolean flag. This lesson therefore models the concept without fabricating a production decision. Lesson 1.1.4 and subsequent lifecycle/invariant lessons will provide prerequisites for verified state and authority evolution.

## Explore — Classify a timeline before accepting its wording

A message or Java record can be named like an event and still only represent a request. Classification requires examining who generated the message, which operation completed, which authority owns the fact, and whether the evidence is local, external or merely asserted.

Use this matrix as the baseline before experimenting:

| Statement | Primary category | Authority/evidence question |
|---|---|---|
| PlaceOrder(customer, basket) | Command | Who requested it, and is the caller authorized? |
| 422 ITEM_UNAVAILABLE | Business rejection | Which local menu rule rejected the attempt? |
| OrderRequestRecorded(O-1) | Local success fact | Did the in-process save return normally? |
| HTTP 201 Location /api/orders/O-1 | Acknowledgement | What resource was created, and did caller receive it? |
| AcceptOrder(O-1) | Future command | Which merchant actor may decide and under what state? |
| OrderAccepted(O-1) | Future merchant fact | Where is authenticated merchant decision evidence? |
| RefundRequested | Could describe a request received | Was it only a request or an approved financial instruction? |
| RefundConfirmed | External operation fact only with appropriate evidence | Does provider confirmation exist for that exact attempt? |
| PaymentAuthorizationTimedOut | Technical observation | Does it say anything conclusive about provider approval? |
| “event=order_intake_recorded” log | Diagnostic log | What was observed, and did storage survive a restart? |

The class of a message is not derivable from its spelling alone. A log called PaymentSucceeded can be wrong. A provider callback can be duplicated, stale or unauthenticated. A local OrderRequestRecorded object is a fact-shaped representation whose exact claim must stay within its observed process-local boundary.

**Independent exercise:** classify each statement by (1) intention, (2) decision/rejection, (3) historical fact, (4) acknowledgement, or (5) technical observation. Then write a one-sentence evidentiary limitation. The interactive lab below will let you vary command eligibility, retries and lost acknowledgements; first predict what will be recorded before you reveal its deterministic model result.



## Predict — Four branches from the same command intention

Take the same request: customer UUID from the demo, restaurant cedar-kitchen, two portions of lentil-bowl, and a syntactically valid JSON body. Before reviewing each outcome, write your predictions for the decision, recorded Order, local success fact, HTTP acknowledgement and remaining uncertainty.

### Branch A: permitted command and normal local save

The synthetic catalog permits the item. The application constructs a new Order intake, saves it, and returns a typed Recorded outcome with a matching OrderRequestRecorded. The existing controller then returns HTTP 201 with Location and pending/no-payment fields.

**Prediction checks:** Is a merchant acceptance fact present? **No.** Has the payment provider run? **No.** Can the same process retrieve the intake by ID? **Yes, provided it remains running and the record is not removed.** Does the local fact survive a process restart independently? **No; it is an in-process value, not a durable event journal.**

### Branch B: valid syntax but ineligible business request

The customer asks for seasonal-special, which is marked unavailable in the server-owned fixture. The command is correctly structured; the application returns a typed Rejected outcome with ITEM_UNAVAILABLE and does not save a new Order or create OrderRequestRecorded. The compatibility HTTP path translates the rejection into the existing 422 response.

**Prediction checks:** Would an OrderPlaced event be truthful? **No.** Is this a server infrastructure outage? **No.** Does it mean a live restaurant actively refused the customer? **No.** It is a deterministic local fixture business rule.

### Branch C: save happened but returned with an exception

A failure-injection repository writes a new intake to its list and throws before returning normally. The handler exposes no Recorded fact to the caller and propagates the infrastructure exception. Inspecting the test repository afterwards reveals that the Order is present.

**Prediction checks:** Can the caller safely classify the command as business Rejected? **No.** Is the absence of a returned event proof of absence? **No.** Does this simulation establish that the actual ConcurrentHashMap always behaves this way? **No.** It teaches a possible exception boundary and the principle of unknown effects.

### Branch D: response lost after normal successful save

The application recorded the Order and produced a local success outcome, but the client never received HTTP 201. From the client's viewpoint there was only a timeout. A retry of the same intent creates another Order with another UUID because the current handler has no durable idempotency mechanism.

**Prediction checks:** Can the client safely infer that the first request failed? **No.** Will reusing X-Request-ID prevent a second intake? **No.** Can we label this duplicate payment? **No—no payment happened.** Is it reasonable to revisit the design when the business requires safe retries? **Yes, after defining the invariant and durability boundary.**

## Engineer — Trace the verified Java implementation line by line

The controller receives HTTP input; the application service makes the decision; the domain Order record describes intake; the repository is process-local; and the HTTP result remains intentionally narrow.

[PlaceOrderOutcome.java](https://github.com/fasiltadesse22/food-ordering-platform-new/blob/225db684a24080f2c4ad1ae6e2f5e259edf0aa7d/src/main/java/com/academy/foodordering/application/PlaceOrderOutcome.java) is a sealed interface with two record variants. **Recorded(Order, OrderRequestRecorded)** must refer to a fact with the same Order ID. **Rejected(code, message)** names an expected business decision and deliberately contains no successful fact. This design makes the positive/negative difference visible to the Java type system rather than relying solely on log wording.

The new public [PlaceOrderService.handle](https://github.com/fasiltadesse22/food-ordering-platform-new/blob/225db684a24080f2c4ad1ae6e2f5e259edf0aa7d/src/main/java/com/academy/foodordering/application/PlaceOrderService.java) catches **BusinessRejection**, returning Rejected. It does not catch every RuntimeException. For success, it calls the existing validation-and-storage logic, waits for the repository save to return, constructs OrderRequestRecorded, and returns Recorded. The old place method maps that typed outcome back to its original Order return or BusinessRejection exception so the established HTTP test contract still applies.

The core method is intentionally simple:

~~~java
public PlaceOrderOutcome handle(PlaceOrderCommand command) {
    final Order order;
    try {
        order = validateCreateAndStore(command);
    } catch (BusinessRejection rejection) {
        return new PlaceOrderOutcome.Rejected(
                rejection.code(), rejection.getMessage());
    }
    var fact = new OrderRequestRecorded(
            order.id(), order.customerId(), order.restaurantId(),
            order.createdAt(), Instant.now(clock));
    return new PlaceOrderOutcome.Recorded(order, fact);
}
~~~

This snippet is explanatory and corresponds to the real linked method; follow the source link for the exact file and surrounding logic. Notice that the name validateCreateAndStore describes a sequence inside one process, not a durable transaction.

### The precise local fact

[OrderRequestRecorded.java](https://github.com/fasiltadesse22/food-ordering-platform-new/blob/225db684a24080f2c4ad1ae6e2f5e259edf0aa7d/src/main/java/com/academy/foodordering/domain/OrderRequestRecorded.java) carries the matching order ID, customer and restaurant references, Order creation time, and an observation time taken after normal save return. The latter is not a commit timestamp from a database, and the record is not persisted independently. There is no event publisher in this application. A local historical claim can be valuable for designing tests and reasoning without demanding Event Sourcing.

[InMemoryOrderRepository.java](https://github.com/fasiltadesse22/food-ordering-platform-new/blob/225db684a24080f2c4ad1ae6e2f5e259edf0aa7d/src/main/java/com/academy/foodordering/infrastructure/InMemoryOrderRepository.java) still uses ConcurrentHashMap. There is no cross-process replication or restart recovery. If the service restarts, previous records disappear, regardless of the meaningful event name.

### Why not introduce a generic command bus?

A generic command dispatcher, asynchronous event queue and plugin-style handler registry would add indirection without solving the current business problem. The first slice has one real command, one local decision point and no consumer requiring decoupled publication. A typed outcome expresses the distinction while preserving direct source traceability and the existing single-deployable architecture.

**Implementation trade-off:** the typed fact is returned to the internal caller, not stored as a separate durable ledger. That avoids a second non-atomic write but cannot answer a future question such as “what was every historical event across all prior restarts?” The correct future solution depends on a validated audit requirement, retention policy, consistency boundary and failure evidence.

## Diagnose — “Success” appeared but no corresponding fact can be found

Treat the complaint as a claim to investigate, not proof that event delivery failed.

**Incident:** a customer sees “Order successful,” but operations cannot find the corresponding order request. The customer supplies a timestamp and screenshot. The backend previously used a process-local repository. Multiple root causes can fit those facts.

### Build a discriminating evidence table

| Hypothesis | What would distinguish it? | Immediate interpretation |
|---|---|---|
| UI confused intake and merchant acceptance | Compare actual response JSON, product wording, and use-case contract | Semantic/customer promise mismatch |
| Request rejected before storage | HTTP status and exact business rejection code | No successful intake on that request |
| Intake was recorded then process restarted | Process restart history and volatile repository state | Expected non-durability, not Kafka delivery loss |
| HTTP response lost after a successful save | Server-side request correlation and prior intake lookup | Client timeout does not establish absence |
| Repeated POST created multiple intake IDs | Distinct Location IDs, access logs and correlation evidence | Known lack of idempotency |
| Infrastructure failed during save | Exception timing and adapter behavior; possible record presence | Outcome may be unknown |
| Restaurant acceptance never occurred | Check for a real merchant acceptance integration and policy | That workflow is not implemented |
| A log said “recorded” but storage evidence is missing | Compare log timing with state and source code | Log observation alone cannot prove durable history |

### A disciplined investigation sequence

First, **identify the precise promised fact**. Was the claim that the platform received a request, saved an intake resource, obtained merchant acceptance, or collected payment? Different facts imply different owners.

Second, **reconstruct the narrow timeline**. Seek the HTTP request identity, response code and Location, exact application checkpoint, relevant process lifecycle, and any available in-process record. Do not assume a correlation header is a deduplication key.

Third, **maintain multiple plausible hypotheses**. A screenshot alone cannot distinguish a lost response from a restart or an incorrect customer promise. Give each hypothesis a specific discriminating observation.

Fourth, **compare actual authority**. The platform owns intake; the merchant would own real acceptance; the provider would own its actual financial effect. The current app has no merchant or provider integrations. Any purported payment success in this application is unsupported.

Fifth, **select the smallest correction justified by the evidence**. If product wording overclaims, fix wording. If the requirement is restart-safe intake, define durability before choosing storage. If safe retry becomes an invariant, specify business-operation identity, concurrency and persistence. Do not deploy Kafka or an Outbox merely because an operator cannot find a local Order after a restart.

Finally, **state what remains unknown**. A careful Staff engineer may conclude: “The customer's screenshot proves what the UI displayed. It does not prove merchant acceptance. We need to inspect the exact HTTP response and process lifetime to determine whether intake was ever retrievable.”

### Counterfactual check

If the platform later gained PostgreSQL, could a 201 always be assumed to mean all downstream systems had processed the event? **No.** A durable local transaction could justify a stronger claim about local state while publication and consumer processing would still be separate boundaries. One added technology changes only the guarantees it actually implements and verifies.

## Defend — Explain the decision at four levels

### To a junior engineer

A command says **“please do this.”** A decision says **“yes, under these rules”** or **“no, because of this reason.”** A fact says **“this specific thing happened.”** An event communicates a meaningful fact. A response tells the caller something about processing. If the customer requests a meal, that is not proof the restaurant accepted it or a payment was made.

### To a senior backend engineer

Our Java PlaceOrderCommand expresses intake intent. PlaceOrderService.handle checks the synthetic menu, returns Rejected for known business invalidity, and otherwise saves Order in the in-memory repository before constructing OrderRequestRecorded and returning Recorded. The place adapter preserves the prior exception-based HTTP contract. A failure after storage may leave an unknown effect; duplicate POSTs create distinct resources. There is no durable event store or external integration.

### To a Staff reviewer

The current architectural force is **truthful command-outcome modeling** within one deployable, not distributed event delivery. Typed outcomes make rejected and successful local decisions explicit, and event naming is scoped to a post-save in-process fact. A second mutable event list would add a non-atomic failure window without providing required durability. A generic broker or event-sourcing architecture would be premature. We would reconsider after defining audit/retention, safe replay, cross-process integration, or measured distribution requirements and verifying a design that enforces the intended invariants.

### To a business stakeholder

When a valid request is submitted, the platform can say that it recorded the requested order for later restaurant review while the current process remains alive. It **cannot** say the restaurant accepted dinner or that payment went through. If the response is lost, support needs an authoritative way to locate the intake; today safe retry and durable lookup are not guaranteed. Clear promises are part of engineering correctness.

### Adversarial questions with bounded answers

**“If a domain event exists, why don't we use Kafka?”** The event is a local descriptive value; Kafka would be a distribution mechanism, not a prerequisite for describing a local fact. We have no approved external consumer or measured reliability force yet.

**“Didn't save already commit the fact?”** The process-local map's save returned normally. That is a local observation, not a crash-durable transactional commit. It does not prove a separate event store would be atomic.

**“Could we return Rejected for every exception?”** No. A write can occur before an exception is thrown; calling that a business rejection incorrectly implies no effect.

**“Why is OrderRequestRecorded a better name than OrderPlaced?”** The former identifies the actual postcondition. The latter could be interpreted as restaurant acceptance or completed checkout under a different organization's vocabulary.

**“What changes if a user presses PlaceOrder twice intentionally?”** Identical payloads alone cannot tell intent from retry. The business needs a defined operation identity and replay policy before deduplicating.

**“Can a provider timeout become PaymentFailed?”** No. A timeout is a communication observation and the provider may have performed the action. Reconciliation or verified provider evidence is required.

**“Could we call these facts an Event Sourcing implementation?”** No. The source of truth is still the Order in a volatile repository, not a persisted authoritative event stream from which state is reconstructed.
