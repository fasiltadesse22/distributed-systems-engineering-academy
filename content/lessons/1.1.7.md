# Lesson 1.1.7 — Guards, Preconditions and Postconditions

**Cluster 1.1 · Chapter 2 · Type A Java engineering + Type D interactive Visual Textbook V2.**

**Engineering question:** What makes a requested transition legal in a particular state?

**Evidence boundary.** The Food Ordering Platform remains a single Java 21/Spring Boot deployable whose only real commerce operation is a process-local order-request intake. Merchant, kitchen, financial-provider, delivery and refund operations are not integrated. This lesson adds a **pure guarded merchant decision evaluator**, an **illustrative preparation gate probe** and side-effect-free application **preview outcomes**. An eligible model transition is a **candidate**, not a merchant acceptance or financial fact. POL-01–POL-10 in the [unresolved business-policy register](../../docs/domain/CLUSTER_1_1_LESSON_1_1_5_DECISION_BACKLOG.md) remain unresolved. Read the [Lesson 1.1.6 lifecycle foundation](1.1.6.md) before interpreting any new guard.

## Orient — A syntactically valid command that is business-illegal

A customer orders a meal. The platform records the request and truthfully reports “Awaiting restaurant decision.” A merchant later rejects because the kitchen is closing. After that rejection, an old client repeats an “accept” command. The command is well-formed: correct JSON shape, known OrderId, recognized action, and possibly even a legitimate merchant operator. But **can an already rejected one-shot merchant decision move to ACCEPTED**? Not under the current illustrative lifecycle. The current state is REJECTED; only PENDING permits an initial ACCEPT or REJECT. Returning HTTP 200 after parsing the command would say nothing about whether the business transition was legal.

Now make the failure harder. A platform employee submits ACCEPT on behalf of the restaurant. The decision is PENDING, the order identity is correct, and the employee is technically authenticated to the platform. Yet authentication answers “who is the caller?” while merchant authority answers “who may commit this restaurant?” A platform employee does not automatically have the restaurant's decision rights. If the application checks only PENDING and a valid token, it has mixed technical access with business authorization.

A third variant has the right merchant operator and a PENDING observation, but the merchant already rejected at its authoritative source. The local guard can pass against stale information while the actual effect would be forbidden. A guard is necessary, but not sufficient for reliable concurrent updates. The **decision-time read**, **write-time atomic enforcement**, and **authentic external evidence** are distinct requirements.

The purpose of this lesson is to build a mechanistic account of legality: identify the requesting actor, the exact entity, the prior state, the business rule, the evidence, the postcondition and the point at which a tentative decision becomes a historical fact. We will derive tests and inspect actual Java outputs for the local evaluator. We will not invent real merchant integration or implement the cross-lifecycle orchestration deferred to later lessons.

## Understand — Six boundaries hidden inside the word “valid”

The phrase “valid command” commonly conceals six different propositions. **Syntax** says the request can be parsed. **Structural validation** says required fields, value ranges and formats are acceptable. **Identity correlation** says the command refers to the intended OrderId, RestaurantId and basket terms rather than an unrelated object. **Authentication** says a trustworthy system has established the caller identity. **Business authorization** says that actor is entitled to make this particular decision for this restaurant at this moment. **Transition legality** says the current state and approved policy permit the requested change. **Authoritative completion** adds one more proposition: the resulting change has been committed or the relevant external source has established its effect.

Consider a perfectly typed RestaurantDecisionLifecycle.Action.ACCEPT. As an enum constant, it always passes a compiler's vocabulary check. That fact does not establish that merchant M-42 owns Order O-17, that the command references the basket revision the merchant reviewed, or that a merchant officer authorized acceptance. Nor does it establish that the decision is still PENDING when a transaction commits. The compiler protects representation, not all commercial obligations.

The reverse distinction matters as well. A command can fail for a normal business reason without being malformed. For instance, accepting an already REJECTED one-shot decision should be an explicit **rejected business outcome**, not a NullPointerException or silent no-op that looks like success. Both the client and the engineer need to know whether input was unintelligible, the actor was unauthorized, the state was ineligible, evidence was missing, or policy remained undecided.

A useful decision narrative therefore traces **request → parse → identify → authenticate → authorize → evaluate preconditions/guards → decide → commit effect → establish postcondition → communicate observation**. Real implementations may combine these steps in-process or split across layers, but the semantic boundaries survive. The Java teaching implementation models the middle decision stage only; the existing intake application handles a different local persisted operation. Do not read a candidate fact label as proof that the entire sequence occurred.

## Understand — Input validation is not a transition guard

A product API may reject a missing order ID, nonnumeric quantity or malformed UUID before business logic runs. That is input validation. A transition guard asks a different question: **given a meaningful request for a real identified entity, can this command alter this particular state under the relevant business rules?** Even perfect validation of an ACCEPT request cannot guarantee that a merchant has not already REJECTED or that the basket terms are still the ones approved.

Compare three cases. Case A: the HTTP body lacks a merchant ID. A boundary validation failure can prevent lookup. Case B: the body contains a well-formed but wrong merchant ID. Parsing succeeds, but identity correlation or actor-scope guard rejects. Case C: identity and role are correct, but the decision is already terminal. The state precondition fails. If the application maps all three to an undifferentiated “invalid input” response, support engineers cannot easily determine whether there is a bad client, an authorization concern or a race. Conversely, publicly revealing too much detail about an unauthorized merchant may expose private information; internal guard diagnostics and public error contracts should not be assumed identical.

The current Java PlaceOrderService contains real request-intake validation: menu item existence, availability, quantity, duplicate lines and arithmetic-safe totals. These validate the platform's own intake contract before saving the snapshot. This lesson does not duplicate or refactor those checks just to generate more guards. Instead, it adds a narrow, **explicitly uncommitted** merchant decision evaluator whose predicates concern actor scope, merchant ownership, expected state, terms and policy.

A guard can read a state value, but some guards need more than state. A PENDING decision may still be impossible to accept if the caller is another restaurant, the command applies to an older basket, or the source of merchant authority is unknown. This is why replacing every guard with an enum switch is insufficient. The state graph tells us which edges are conceivable; a guard tells us whether an edge is legal for this actor and this evidence at this decision boundary.

## Understand — Authentication, authorization and business fact authority

Authentication is a procedure that associates a request with a verified principal through credentials, keys, sessions or other trusted evidence. Authorization evaluates whether the authenticated principal has permission for a particular action and resource. Business fact authority goes further: the relevant participant or contract is the legitimate source for the fact being asserted. A platform administrator can have broad technical permissions without the legal or commercial authority to declare that a restaurant accepted food preparation.

In the conceptual merchant flow, four questions must be separated. Who submitted the request? Has that identity been technically authenticated? Does that actor belong to the correct restaurant and have the required role? Does the actual restaurant source attest a decision about the correct basket and merchant agreement? Matching a string such as “cedar-kitchen” is not proof of a legitimate merchant credential. A boolean named authenticated is not a production authenticator. In the actual Java evaluator, these booleans are explicitly **classroom assumptions** supplied to a pure function; a passing guard cannot be transformed into a real merchant signature.

A wrong-actor case helps reveal the difference. Customer C-1 presses a button that sends ACCEPT. The OrderId, requested restaurant and state may all be correct, yet the actor role is CUSTOMER instead of MERCHANT_OPERATOR. The guard ACTOR_ROLE fails. Another case uses a technical session for an actual merchant operator, but the operator is only authorized for M-99 while the decision belongs to M-42. ACTOR_SCOPE fails. A third case authenticates a merchant operator for M-42 but lacks permission to make binding decisions. BUSINESS_AUTHORITY_ASSUMED fails independently of the authentication guard.

Production authorization typically runs at a trusted application boundary and may use roles, attributes, policies, contractual ownership and revocation. The business domain should receive verified claims or evidence rather than trust raw client flags. This lesson's teaching implementation demonstrates the **logical separation** of those checks, not secure authorization architecture. In particular, do not expose a preview's role and evidence booleans as an endpoint allowing customers to self-approve decisions.

## Understand — Preconditions, postconditions and invariants have different scopes

A **precondition** is what must already hold for an operation to be considered. For illustrative merchant ACCEPT, the identified RestaurantDecision must be PENDING; the actor must be a merchant operator for the same restaurant; the basket terms must match; and an explicit classroom policy assumption must be selected. A precondition is evaluated against a particular state and evidence snapshot, not against an eternal truth. If the relevant source changes after evaluation, the next operation may no longer be eligible.

A **postcondition** specifies what the operation promises when it returns successfully within its defined boundary. For a **pure transition evaluator**, the strongest postcondition is local: the candidate next state is ACCEPTED, OrderId and RestaurantId remain identical, every required guard passed under its supplied assumptions, and the returned candidate label is illustrative. This does **not** promise that the restaurant actually accepted, that the repository committed, or that any network message was delivered. Those would be different operations with different preconditions and postconditions.

A **business invariant** must remain true across every permitted state and transition within its owner boundary. Identity continuity is an example: an existing merchant decision cannot change its OrderId during a transition. Another invariant is that a rejected evaluation must preserve the exact prior immutable decision and emit no candidate success fact. The model enforces these in result constructors as well as tests, ensuring later callers cannot accidentally create inconsistent success/rejection pairs.

The distinction matters when debugging. “A merchant was authenticated” may be a checked precondition, not a fact of successful acceptance. “The decision next state is ACCEPTED” is a pure model postcondition, not necessarily a committed business fact. “No transition may silently change OrderId” is a persistent domain invariant that applies to accepted and rejected paths. Mixing these categories makes technical guarantees stronger on paper than they are in running software.

A postcondition should be falsifiable. Write tests asserting **before is unchanged**, **next has the expected state**, **same typed identities**, **candidate label present only on success**, and **rejection returns the exact before object**. The tests establish the pure contract. A separate integration test would be required to establish a database write, and a real merchant integration would need independent external source evidence.

## Understand — Build a total transition decision function

A total decision function produces a meaningful result for **every action/state/context combination** within its declared input vocabulary. It must not fall through silently, return a null state, manufacture a success fact after rejection, or assume that the happy path is the only path. In an illustrative merchant model, both ACCEPT and REJECT are legal only from PENDING under specified assumptions. In ACCEPTED or REJECTED, a second decision is rejected. In a preparation guard probe, START_PREPARING and COMPLETE_PREPARATION have distinct required current stages.

Conceptually, the function has the shape **evaluate(current, action, actor, evidence, teachingPolicy) → AcceptedCandidate or Rejected**. The accepted branch carries the same identity, a proposed next immutable snapshot, an ordered list of successful guard explanations, and a candidate label. The rejected branch carries an explicit reason, the same original snapshot, and no candidate success fact. This is more expressive than a boolean because debugging, testing and user communication require the reason and proof boundary.

What makes the result **total**? At least three things. The allowed action vocabulary is closed or exhaustively mapped, including terminal-state cases. Every required guard produces a defined pass/fail observation even when another guard already failed, so the inspector can show the complete evaluation surface. The result constructor rejects malformed combinations such as “rejected=true but a success fact is present” or “accepted=true while one guard failed.” For programming errors such as passing null where the API contract requires a non-null value, a precondition exception can still be appropriate. Totality concerns the modeled business decision domain, not arbitrary invalid Java invocations.

A domain transition should avoid side effects during the decision phase. If it writes a database row before checking all guards, a late guard failure can leave partially mutated state. If it calls an external provider to see whether payment can succeed, it may trigger a financial operation during what developers thought was validation. This lesson's evaluators are pure and contain no repository or network dependencies, allowing us to test decision logic without accidentally executing commerce.

Later integration must still ensure the decision is checked against authoritative, current state and committed atomically where necessary. A pure total function is the core of a robust transition, but not its entire operational guarantee.

## Understand — Preserve identity and actor scope through every result

In a transactional system, the identity that a command targets must be explicit. An OrderId identifies the platform intake resource, and RestaurantId identifies the merchant decision scope. A command for Order O-17 must not accidentally manipulate Order O-18 because the payload, URL, cached context or authentication token differ. Similarly, a request for Restaurant M-42 should never be evaluated as acceptance by Restaurant M-99 just because they happen to share a display name or an operator.

The Java evaluator checks **IDENTITY_ORDER** and **IDENTITY_RESTAURANT** before evaluating role and state. It then checks **ACTOR_SCOPE** to distinguish the request's target merchant from the actor's asserted merchant affiliation. These are independent predicates. If the target decision belongs to M-42 but the actor identifies with M-99, scope fails even if the request merchant field correctly says M-42.

Identity preservation is also a postcondition. An accepted candidate creates a new immutable RestaurantDecisionLifecycle object, but the OrderId and RestaurantId values remain the same. On rejection, the evaluator returns the exact same original record instance and a null candidate fact. That stronger no-op guarantee helps catch accidental mutation and fact emission. It does **not** establish that some other thread or process did not mutate a different authoritative store.

Consider an eventual payment attempt. PaymentAttemptId is separate from OrderId and may have several attempts for one order. A merchant ACCEPT command cannot legally promote PaymentAttempt PA-3 into CAPTURED; those are distinct authority boundaries. This lesson's guard evaluator does not manipulate PaymentAttemptLifecycle, because its task is to validate transition legality within a narrowly scoped merchant model. It should not introduce cross-entity orchestration simply to satisfy the teaching diagram.

## Understand — State-only guards versus context-dependent guards

A state-only guard might say **only PENDING may receive ACCEPT**. This is necessary but insufficient. A context-dependent guard must inspect identity correlation, actor role, business authority, offered basket terms, evidence authenticity and policy scope. These checks can pass or fail independently, and their inputs have different trustworthiness. If a user supplies a boolean “I am authorized,” that is a claim, not verification.

For an illustrative one-shot merchant decision, the state-only rule can be expressed as **state == PENDING**. The context-dependent conjunction might be: same OrderId; same RestaurantId; merchant-operator role; actor associated with the same merchant; authenticated identity assumed; merchant decision rights assumed; expected observed state matches; basket terms assumed identical; external evidence assumed; explicit educational POL-02 mode. Each predicate has a distinct explanation and negative test.

State-only and contextual guards serve different purposes. The former expresses legal topology of the lifecycle graph: from ACCEPTED there is no one-shot ACCEPT edge. The latter expresses applicability under a particular actor and situation: even from PENDING, a customer cannot decide for a restaurant. Conflating both into the state name produces monstrosities like PENDING_MERCHANT_AUTHENTICATED_BASKET_VERIFIED that depend on transient actor context rather than persistent business lifecycle.

In a real implementation, actor authorization must be evaluated from trusted authentication and authorization systems, and policy must be an approved versioned rule. Basket-match evidence must refer to the actual commercial terms considered. A local state snapshot must be current at the point of effect. The Java context deliberately names its inputs “assumed” so the reader cannot mistake the exercise for deployed security or merchant connectivity.

## Understand — Reconcile blueprint PLACED with actual Java REQUESTED and PENDING

The Cluster 1.1 blueprint illustrates **AcceptOrder(current=PLACED)**. The current Food Ordering Platform does not have an OrderLifecycle.State called PLACED. Its real Order is an immutable platform-local intake snapshot with a typed **REQUESTED** lifecycle view. The separate illustrative RestaurantDecisionLifecycle begins **PENDING** and permits a one-shot ACCEPT or REJECT under explicit assumptions. Silently renaming REQUESTED to PLACED would blur the business boundary between “platform recorded intent” and “restaurant accepted commercial commitment.”

A truthful translation of the blueprint example is: **Order O-17 is REQUESTED (real local intake)**; **RestaurantDecision for O-17/M-42 is PENDING (illustrative local model)**; **a merchant operator for M-42 proposes ACCEPT**; **the pure guard evaluator checks identity, role, expected state, terms, evidence and an educational POL-02 assumption**; **if every guard passes, it returns an ACCEPTED candidate**, not an external merchant fact. The application has not sent a merchant request or modified the persisted Order resource.

Where is the commit point? **There is none in this evaluator.** Its returned candidate lives in memory until a future authorized application boundary enforces the decision and persists a state transition. By contrast, the existing PlaceOrderService's real local intake completion point is the successful return from repository.save; OrderRequestRecorded is constructed after that local save. Even that is process-local storage without durable external guarantees. An accepted pure transition therefore must never be represented as equivalent to that post-save fact.

This mapping is central to engineering credibility. When the blueprint uses generic domain language, we should map it to the actual verified model and state exactly what is hypothetical. We should not alter production code or approve business policy simply to make a teaching example syntactically identical to the roadmap.

## Explore — Trace the illustrative ACCEPT command across eleven guards

Follow the visual guard trace embedded beside this section. The learner selects the lifecycle state, action, actor role, claimed merchant identity, authentication assumption, business authority assumption, basket-match assumption, evidence assumption, expected state and policy mode. The inspector shows **all eleven guard checks**, in their declared order, with pass/fail explanations. This is a deterministic mirror of the Java pure evaluator, not a live execution of a merchant gateway.

The sequence begins with **IDENTITY_ORDER**: does the target command refer to the same OrderId as the decision? Next **IDENTITY_RESTAURANT** checks the requested merchant against the owner. **ACTOR_ROLE** and **ACTOR_SCOPE** separate a merchant representative from a customer or platform employee, and ensure the representative belongs to the merchant being decided for. **AUTHENTICATED_ASSUMED** asks whether the classroom scenario assumes a verified principal. **BUSINESS_AUTHORITY_ASSUMED** checks the separate entitlement to decide. Neither boolean constitutes production security.

**EXPECTED_STATE** compares the scenario's locally observed expected state with the current immutable snapshot. This can detect a knowingly stale input; it is **not** atomic compare-and-swap. **STATE_PENDING** enforces the one-shot decision topology, rejecting ACCEPT after an existing REJECT. **BASKET_TERMS_ASSUMED** requires matching commercial terms. **MERCHANT_EVIDENCE_ASSUMED** acknowledges that no real merchant source has been connected. Finally **POL_02_EDUCATIONAL_ONLY** blocks a candidate when the business policy mode is unresolved rather than explicitly assumed for the lesson.

All checks are evaluated and reported. If several fail, the **first failed rule in stable order** is selected as the explanation, but the inspector still shows later failures. This is a learning-friendly evaluation contract, **not a recommendation to disclose every failed identity or authorization test to an untrusted HTTP client**. The result is either an illustrative candidate or a rejection that preserves the original snapshot and emits no candidate fact.

## Understand — Accepting an already rejected decision must remain rejected

Start with RestaurantDecision(O-17, M-42, REJECTED). The command ACCEPT is syntactically valid. The actor might be an illustrative authenticated merchant operator. The requested OrderId and RestaurantId can match perfectly; the basket terms may be unchanged. Nevertheless **STATE_PENDING fails** because the decision is terminal in the present one-shot teaching model. A command does not rewrite the prior business history merely because its caller is authorized.

The guard evaluator also checks an explicitly stated expected state. If the caller still expects PENDING, **EXPECTED_STATE fails**, showing how stale observation can be detected before the state-only rule runs. If the caller expects REJECTED, EXPECTED_STATE passes but STATE_PENDING still fails. The two negative outcomes teach different mechanisms: *stale view* versus *illegal transition from correctly observed state*. Neither produces an ACCEPTED candidate, and both return the unchanged REJECTED object.

There are legitimate real-business possibilities that might look like a second acceptance: a merchant reverses a rejection under policy, the customer revises the basket, or the platform creates a new offer. Those require new explicit authority, identity/version terms, commercial obligations and tests. We must not silently insert a REJECTED → ACCEPTED edge simply because it would make a simulated scenario more convenient. POL-02 is still unresolved, so the model's one-shot terminality is an educational assumption.

The operator-facing diagnosis should also distinguish an **adapter mapping error** from a business transition error. A transport field could say “Accept” while the application maps it to a different action. The guard trace should record the actual parsed action, source identity and expected state. Without that evidence, a wrong HTTP response could be misdiagnosed as a flawed state machine.

## Understand — Trying to prepare food before merchant acceptance

Consider a kitchen operator attempting START_PREPARING while the merchant decision is still PENDING. Even if a physical kitchen could begin work, the business needs an approved preparation gate and a legitimate merchant commitment. Under the **illustrative preparation policy used only for learning**, the guard MERCHANT_ACCEPTED fails, so the probe reports ineligible, preserves the original NOT_STARTED stage and emits no candidate preparation fact.

A key nuance: this is not a production-ready Restaurant-to-Kitchen orchestrator. The current Java application has no kitchen integration, no preparation record, no provider confirmation, and no approved POL-04. The Java PreparationGuardProbe is intentionally a **pure probe** over supplied hypothetical facts. Its six checks include matching OrderId, kitchen actor role, merchant ACCEPTED state, an evidence assumption, current preparation stage and an explicitly selected educational policy. All passing means **eligible under these assumptions**, not that physical work began.

Change only the actor to CUSTOMER. The merchant might be hypothetically ACCEPTED and the preparation stage NOT_STARTED, but KITCHEN_AUTHORITY fails. Change only the merchant source evidence assumption to false: MERCHANT_EVIDENCE_ASSUMED fails. Change only policy mode back to unresolved: POL_04_EDUCATIONAL_ONLY fails. These counterfactuals demonstrate that a passing state graph edge is not enough to justify an external effect.

The exercise must also explain the meaning of a rejected probe. The returned stage remains NOT_STARTED because the probe never mutates an authoritative kitchen store. In a real business, the kitchen might still have started due to an unobserved physical action; our local no-op result does not prove nothing happened outside the system. That is why reliable state transitions require source evidence and coordination, subjects developed more deeply later.

## Understand — Attempting completion before preparation

Now examine COMPLETE_PREPARATION when the hypothetical kitchen stage is NOT_STARTED. The operator is correctly identified, the merchant is hypothetically ACCEPTED, and the educational policy is enabled. The requested transition nevertheless violates the **CURRENT_STAGE** guard, because completing food that the system has not established as PREPARING contradicts the state-machine contract.

A different illegal case begins at READY and attempts COMPLETE_PREPARATION again. The same guard rejects because the model expects PREPARING. Rejection must preserve the existing stage exactly and create no second “completed” candidate. This prevents an ambiguous no-op from being mistaken for new evidence. In a real integration, duplicated messages might need idempotent acknowledgement or deduplication, but those are separate runtime policies and identity questions rather than an excuse to manufacture another completed fact.

When the stage is PREPARING and merchant acceptance is assumed, the illustrative probe may say eligible for READY. Yet there remains no kitchen state write or actual food inspection. The stage of physical preparation can differ from a locally observed stage, and the real business may have food-safety, quality, timeout or staff authorization rules missing from this tiny model. The probe illustrates the legal transition structure; it is not a complete fulfillment implementation.

This example is useful because it distinguishes **a structural order constraint** (“preparation must precede completion” in a chosen model) from **an authorized policy rule** (“who is allowed to mark it complete, when, and with what evidence?”). Both belong in an eventual production guard, but the latter cannot be approved by the engineering team alone. Do not prematurely build Lesson 1.1.9's full lifecycle composition.

## Explore — Derive total decision tables rather than ad hoc if statements

The merchant machine has three states and two actions, which produce six state/action pairs **before** actor, identity, terms and policy dimensions. Under the explicitly chosen educational one-shot assumption, the state-only topology is:

| State before | ACCEPT | REJECT | Meaning |
|---|---|---|---|
| PENDING | Candidate ACCEPTED | Candidate REJECTED | Only if all contextual guards also pass |
| ACCEPTED | Rejected / unchanged | Rejected / unchanged | Terminal teaching state |
| REJECTED | Rejected / unchanged | Rejected / unchanged | Terminal teaching state |

This table answers only the **state topology** question. A complete decision table extends each candidate edge with authenticated and authorized merchant actor, matching restaurant and Order IDs, matching basket terms, source evidence and educational policy. Any failed contextual guard changes the apparent “candidate” cell into a **rejected/no-op** result. The test matrix must therefore include *each independent failure cause*, not just two happy paths.

The preparation probe has three stages and two actions. Under an assumed accepted merchant and eligible kitchen actor, its table is:

| Stage before | START_PREPARING | COMPLETE_PREPARATION |
|---|---|---|
| NOT_STARTED | Candidate PREPARING | Rejected / unchanged |
| PREPARING | Rejected / unchanged | Candidate READY |
| READY | Rejected / unchanged | Rejected / unchanged |

Again, these are **hypothetical local tests**, not proof of actual preparation or an approved POL-04. Consider the full cross-product: actor could be CUSTOMER, PLATFORM or KITCHEN_OPERATOR; merchant decision could be PENDING, ACCEPTED or REJECTED; source evidence could be available or unknown; educational policy could be enabled or unresolved. Enumerating a representative set of independent guard failures is more useful than testing every combinatorial context blindly. The most important property is that every disallowed case returns the original phase and no fact, while every educational candidate retains identity and explains its limited scope.

Parameterized JUnit tests follow directly from these rows and contextual counterexamples. Test names should describe the rule being proved rather than simply the method executed.

## Understand — Guard ordering, first failure and information disclosure

Multiple guards can fail simultaneously. Suppose the target RestaurantId is wrong, the caller is unauthenticated, and the state is already REJECTED. Which error should be returned? There is no universal answer: the behavior depends on trusted boundary, security policy and intended diagnostic audience. The local teaching evaluator evaluates all eleven guards and reports a stable **first failure** for explanation, making the rule ordering explicit and testable.

In a real HTTP endpoint, evaluating all guards may have side effects such as information disclosure, timing differences or wasted remote lookups. A privacy-preserving boundary might authenticate first, verify broad resource access without revealing existence, then load the entity and run business guards. The public response might intentionally be less specific than the internal decision trace. Our current Java class has no HTTP endpoint and receives assumption booleans; it is suitable for studying *logical rule independence* rather than implementing a secure access-control pipeline.

Error precedence can also affect customer experience. “You cannot accept this order because it was already rejected” is meaningful to an authorized merchant, but it would reveal another merchant's order history to an unauthorized caller. A production design might return a generic denial to the latter while logging the precise internal guard result. This distinction reinforces the difference between domain result and transport mapping—one of the diagnostic questions in the blueprint.

Changing guard order should be a deliberate design decision. If we introduce a new business policy later, tests should cover its precedence against existing failures and its effect on customer-facing semantics. Simply appending an if statement may accidentally expose a secret, change error codes or accept a transition that should remain blocked.

## Understand — Side-effect-free rejection and legitimate fact emission

A rejected transition has three key postconditions: **accepted is false**, **next state is the exact original state object**, and **no success fact is emitted**. These are stronger than merely checking that the state enum equals its previous value. A different object with the same enum might contain changed identity, version, amount or other hidden fields; a rejected operation must not silently rewrite those fields. The local evaluator's immutable record and defensive result constructor make this contract explicit.

For an accepted educational candidate, the evaluator constructs a new immutable state snapshot with preserved OrderId and RestaurantId. The returned label begins with **CandidateIllustrative** to make its status unambiguous. It is not persisted, authenticated or externally attested. If a developer instead named it RestaurantAccepted and published it as a fact, downstream systems and customer screens could reasonably—but incorrectly—treat the simulation as a commercial commitment.

The *actual* Java application already illustrates a genuine local fact boundary in PlaceOrderService. It validates the intake command, saves to an in-memory repository and only after successful save constructs OrderRequestRecorded. That historical label refers to the platform's local process, not a merchant's action or durable global event. The new PreviewRestaurantDecisionService has no repository, external adapter or publisher, so it cannot create an equivalent fact.

Negative tests should assert the absence of candidate facts, not just a false result. If an unauthorized command emits a success event and then returns a business rejection, the system has already created a contradiction. A correct pure evaluator makes success labels depend on all guards passing, and no label is produced for rejected decisions. Real side-effect prevention would additionally need the application to avoid persistence and external calls on rejection.

## Understand — A passing pure guard is not a persistence commit

Imagine an evaluator returns a candidate ACCEPTED state at T1 after reading PENDING. At T2 a different actor rejects the decision in the authoritative store. At T3 the first caller writes ACCEPTED based on its stale candidate. A correct pure function was used at T1, but the final update is still invalid because the world changed before commit. This is a **time-of-check/time-of-use** problem: a legal transition when assessed may be illegal when applied.

The exact commit point depends on storage semantics. For a local database aggregate, a typical approach would atomically compare the expected version/state while writing the new snapshot in one transaction, then emit a fact only after a successful transaction boundary. For remote merchant authority, no local compare-and-set can substitute for authenticated merchant decision evidence and an agreed protocol. Those are **future engineering requirements**, not features added in this lesson.

The current evaluator has an EXPECTED_STATE check, but that only compares caller-supplied expected state with the current immutable object passed to the function. It does not lock the database, compare a repository version, or prevent another process from changing the authoritative state after the call. The teaching interface must say so. Likewise, a successful HTTP request to a service would not necessarily prove durable commit or external execution; acknowledgements require precisely scoped semantics.

At the lesson boundary, the result of a pure evaluation is a *candidate* suitable for testing and design review. There is no new merchant repository and no new order mutation endpoint. That is intentional: first establish legality and its proof obligations, then in the appropriate lesson introduce production persistence and concurrency controls when the verified requirements justify them.

## Understand — Stale states, conflicting observations and commit-time checks

A stale read can create an illegal transition even when the guard logic is perfect. Consider two operators who both observe PENDING at the same time. Operator A proposes ACCEPT; operator B proposes REJECT. Each pure evaluation passes against its own PENDING snapshot. The business may permit only one terminal decision. If both candidates are written without an atomic conflict check, the final state depends on interleaving, and the system may emit incompatible facts.

A second scenario involves a delayed merchant message. The platform has local PENDING, the merchant source has already decided REJECTED, and a platform-side classroom ACCEPT evaluation returns eligible. That output is not a source fact. The real resolution depends on authenticated source truth, revision identity, legal decision timing, and possibly reconciliation. A locally computed expectedState comparison cannot supply missing merchant evidence.

A third scenario is **adapter mapping error**. The transport receives a string meaning “reject,” but its adapter maps to ACCEPT. Every guard for ACCEPT might pass because the state and actor are eligible, yet the wrong business intent is executed. The problem is outside the transition guard: the adapter misrepresented the command. Integration tests must therefore verify that the external request maps into the intended domain action and that the response maps back into truthful customer language.

The lesson diagnoses these risks without implementing later concurrency experiments. Version checks, atomic updates, retries, message identity, distributed conflicts and external reconciliation will require their own verified contracts. Here the learner must identify the failure window and explain what additional mechanism would be required to close it, not claim that a local if statement solved distributed consistency.

## Understand — Cross-lifecycle guards require independent evidence

A merchant ACCEPT may depend on financial authorization under one candidate commercial policy, while another policy may allow merchant acceptance before payment. Neither policy is currently approved (POL-01). A kitchen START_PREPARING may depend on merchant acceptance and payment guarantees; POL-02 and POL-04 remain unresolved. A refund instruction after a rejected paid order depends on POL-05 through POL-07. Therefore **cross-lifecycle guards are not simply local enum comparisons**: they require the correct source identities, evidence, policy version, observation freshness and an explicitly chosen decision authority.

Suppose a platform sees RestaurantDecision ACCEPTED in a purely illustrative Java object. It cannot infer that a real restaurant authorized preparation. Suppose it also sees PaymentAttempt AUTHORIZED. It cannot infer capture or settlement. A derived workflow predicate such as “merchant accepted and payment authorized” describes a model snapshot under assumptions, not a guarantee of a legally permissible kitchen action. An engineering implementation must not promote those assumptions into production business policy.

The preparation guard probe intentionally keeps the problem small: it models **structural prerequisites** and requires an explicit hypothetical educational POL-04 mode. It does not initiate a payment attempt, change an Order, persist kitchen state or create an external side effect. That preserves the independence established in Lesson 1.1.6 and avoids prematurely implementing the full composition planned for Lesson 1.1.9.

A useful engineering rule is to write *where each guard's evidence comes from* before coding it. If the source is currently only a mock or learner-controlled boolean, document that limitation. If the source is truly external, identify how it is authenticated and correlated. If the business owner has not approved the policy, the rule should remain blocked or clearly hypothetical. A guard's correctness depends on evidence and authority as much as on its Boolean expression.

## Explore — Change inputs in the live guard inspector

The guard studio is designed for controlled counterfactuals. Start with the default illustrative merchant ACCEPT path: current PENDING; requested action ACCEPT; matching OrderId/RestaurantId; merchant-operator role; matching merchant scope; authentication, business authorization, terms and source evidence assumed; expected state PENDING; educational POL-02 enabled. The result should be an **eligible candidate**, with all eleven checks visibly passing and an ACCEPTED proposed next state. No real merchant action occurs.

Now change exactly one variable. Switch the actor to CUSTOMER: ACTOR_ROLE fails. Restore the role and disable business authorization: BUSINESS_AUTHORITY_ASSUMED fails independently of authentication. Restore authority and choose the wrong restaurant identity: ACTOR_SCOPE fails. Choose current REJECTED: STATE_PENDING fails. Change expected state back to PENDING while the actual scenario state remains REJECTED: EXPECTED_STATE also fails. Disable educational policy: POL_02_EDUCATIONAL_ONLY fails. In each rejected case, the before/after view must show identical state and **no candidate fact**.

The next exercise changes to the preparation probe. Select START_PREPARING while merchant PENDING: MERCHANT_ACCEPTED fails, preserving NOT_STARTED. Select COMPLETE_PREPARATION while stage NOT_STARTED: CURRENT_STAGE fails, preserving NOT_STARTED. Select KITCHEN_OPERATOR, accepted merchant, assumed evidence, and educational POL-04: a stage change may be proposed, but no real preparation work has occurred. The diagram must label the output as a **candidate**, not an implementation or external result.

The studio shows all evaluated guards, not merely a green/red badge. Students should ask which guard is decisive, which others are also false, what independent evidence could establish each premise, and what remains unresolved at policy level. Repeatedly changing one variable builds a causal understanding of transition legality.

## Predict — Before/after, fact/no-fact and the counterexample discipline

Before revealing the result, predict for each scenario: (1) the decisive guard; (2) the decision; (3) the original state; (4) the next state; (5) whether any candidate fact is allowed; (6) whether the result establishes a real business effect; and (7) which policy remains unresolved. A good answer distinguishes **candidate eligibility** from **committed business success** even when every local guard passes.

Consider an authenticated merchant operator for the correct restaurant whose source evidence assumption is false. It is tempting to approve because the state and actor are otherwise correct. The correct model rejects: source evidence is missing, and the customer should not be promised merchant acceptance. Consider a kitchen operator who tries to complete before starting: the command vocabulary and authority may be correct, but the current-stage precondition is not.

Counterexamples reveal hidden assumptions. If a test checks only that ACCEPT from PENDING returns ACCEPTED, it will miss wrong-restaurant authorization and missing basket evidence. If it checks only that a terminal decision rejects, it may miss a candidate fact accidentally emitted on the rejected path. If it checks only before/after enum equality, it may miss changed identifiers. Each legitimate guarantee should have at least one positive case and one independent negative case.

The interactive prediction exercise is deterministic and based on the same rules documented in the Java contract. It cannot create external effects, and it should not be used as a substitute for JUnit or packaged Spring Boot verification. Its educational value lies in making the assumptions, failure branches and precise postconditions inspectable.

## Engineer — Trace the real Java evaluator and application outcomes

Start at the immutable Java Lesson 1.1.6 baseline. OrderLifecycle knows the narrow local NEW → REQUESTED intake decision, while RestaurantDecisionLifecycle and PaymentAttemptLifecycle model independent hypothetical lifecycles. Existing public OrderController POST/GET behavior remains intact. Lesson 1.1.7 adds new classes rather than changing those verified APIs or authorizing external business operations.

The **GuardedRestaurantDecision** class evaluates eleven explicit checks and returns an immutable Evaluation containing original decision, next decision, action, pass/fail guard list, rejection reason and optional **CandidateIllustrative** label. On a failed guard, it returns the original object and null label. On success, it delegates to the existing one-shot RestaurantDecisionLifecycle transition but wraps its illustrative label as a candidate. Its constructors enforce identity continuity and reject logically inconsistent results. All these outputs are **pure local data**.

The **PreviewRestaurantDecisionService** in the application layer converts a pure evaluation into sealed **Eligible** or **Rejected** outcomes. There is no repository, network client, Spring endpoint or event publisher. This makes application handling explicit while protecting the boundary between *previewing legality* and *committing a business decision*. The **PreparationGuardProbe** independently checks illustrative kitchen start/completion prerequisites without introducing an actual kitchen lifecycle module.

The **GuardCheck** record makes the entire decision surface inspectable: named rule, Boolean result and explanation. This supports table-derived tests and meaningful learning visualization. The approach is intentionally modest. It preserves the single-deployable modular-monolith evolution without manufacturing microservices, durable messages, payment providers, merchant integrations or a policy engine.

The applied engineering walkthrough and frozen checkpoint link the Java source and actual CI runs by immutable commit. Never describe those classes as actual restaurant acceptance or preparation APIs. A passing Maven suite can prove the pure model's behavior and the existing intake regression, but not the authority of absent external actors.

## Verify — Derive executable tests from rules, not controller responses

A parameterized test suite should be derivable from the decision tables before looking at controller code. For the merchant model, enumerate both valid PENDING actions under explicit educational assumptions. Assert a new next-state candidate with preserved OrderId and RestaurantId, every guard passing, an illustrative candidate label and an unchanged original object. Then test each independent failure source: wrong OrderId, wrong requested RestaurantId, customer/platform actor, actor belonging to another restaurant, unauthenticated identity, missing business authorization, stale expected state, mismatched basket terms, missing source evidence and unresolved policy. Each must reject, return the same object and emit no fact.

Test the legal state topology across PENDING, ACCEPTED and REJECTED. Only PENDING is eligible under the one-shot assumption. If the current decision is already REJECTED and the caller expects REJECTED, the failure should be STATE_PENDING rather than only stale expectation; that distinction shows the correct failed precondition. Tests also verify the defensive result constructor cannot accept a rejected result carrying a fabricated success label.

For preparation, derive table rows for START_PREPARING from NOT_STARTED and COMPLETE_PREPARATION from PREPARING, then the invalid stage/action pairs. Add the contextual cases: wrong actor, merchant pending/rejected, missing evidence, unresolved policy. None should mutate the stage on failure. A successful classroom probe carries an illustrative candidate label and explicitly states **NO kitchen command**.

Finally rerun the full Java Maven suite, package the Spring Boot jar, and smoke-test the existing HTTP 201 and 422 intake paths. No new HTTP endpoint is justified by this lesson. In the React academy, verify content integrity, TypeScript, unit tests, production build, desktop Chromium controls, before/after views, navigation, theme and earlier lesson regressions. **Do not claim results until CI outputs and commit SHAs exist.** Old tests should remain green.

## Diagnose — Illegal acceptance: missing guard, stale state or adapter mapping?

An incident report says: “The restaurant had rejected the order, but the customer later saw it accepted.” Resist the temptation to prescribe an enum check without evidence. Obtain exact OrderId, RestaurantId, basket version, actor identity and authorization scope, incoming action, observed state and its source, evaluation-time guard trace, attempted write outcome, committed state/version if any, and customer projection source and freshness.

**Hypothesis A — missing business guard:** the system actually permitted ACCEPT from REJECTED or omitted the authorized-merchant check. Evidence: the committed source decision was REJECTED before evaluation, and the guard trace either lacks STATE_PENDING or incorrectly passes it. Reproduce via table-derived test. Repair the rule, identify affected operations and guard against repeating the same invalid effect.

**Hypothesis B — stale-state race:** the guard correctly evaluated PENDING, but another authorized actor committed REJECTED before the acceptance write. Evidence: two competing decision attempts, snapshots or versions, and a late write without atomic conflict enforcement. The pure evaluator is not itself wrong; the application commit protocol is insufficient. Later concurrency lessons will implement and verify the relevant mechanism.

**Hypothesis C — adapter/transport mapping:** the input was REJECT or belonged to a different merchant, but an adapter mapped it to ACCEPT or the wrong OrderId. Evidence: trace of original request, parsed action, correlated identity and application command. The guard may have evaluated exactly what it received; the input transformation was incorrect. Fix mapping and test through the adapter boundary.

A fourth possibility is **stale customer projection**: the authoritative merchant never accepted after rejection, but the UI displayed a delayed old accepted observation. The correct remedy is projection ordering and fact-source reconciliation, not changing the domain guard. In the current Java application, all merchant actors remain hypothetical; this is a production diagnosis exercise, not a claim that such an incident occurred.

## Defend — A Staff reviewer proposes an exception policy

During design review a Staff engineer asks: “Suppose we allow a restaurant to reverse rejection within two minutes if the basket is unchanged and the customer has not been charged. Can we just add REJECTED → ACCEPTED?” A reliable architect should resist the shortcut. First ask **who can approve that policy**, how it changes the customer promise, what constitutes an unchanged basket, how provider outcomes are correlated, and whether compensation or customer notification is required. POL-02 and other cross-lifecycle policies are still unresolved, so no production rule is approved by this discussion.

For the hypothetical exercise, version the proposed exception rule. Add a distinct action such as REQUEST_RECONSIDERATION or a new decision identity rather than silently broadening ACCEPT. Define source authority, time-window semantics, basket-version equality, customer consent and financial evidence. Construct a new decision table identifying which prior states and facts permit the exception. Then add positive and negative parameterized cases: inside/outside window, wrong actor, changed basket, unknown financial outcome, concurrent terminal decision, and repeated request. Require preservation of state and fact absence for each rejection.

Next analyze the commit boundary. A two-minute rule evaluated against an old timestamp can pass locally but fail at write time. If the merchant source has a definitive decision, the platform cannot override it unilaterally. If financial evidence is unknown, a policy may block until reconciliation. This is an example of how business-rule changes interact with authority, versions and coordination; it should not be implemented until an accountable policy owner approves it.

At Staff level, compare alternative designs: an explicit override action with audited reason; a new amendment lifecycle; a merchant decision version with supersession semantics; or keeping terminality and requiring a new order offer. Explain their operational trade-offs and the evidence that would justify one. The important skill is coherently revising **contract, guards, tests, UI wording and source authority**, rather than adding one permissive edge.
