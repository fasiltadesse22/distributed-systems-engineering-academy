# Lesson 1.1.4 — Business Identity and Authoritative State

**Engineering question:** Which identities are stable, and which component is entitled to determine a fact?

**Cluster 1.1 · Chapter 1 · Type A:** Persistent Java platform evolution paired with an evidence-based Visual Textbook V2 chapter.

**Dependency:** Lessons 1.1.1–1.1.3 established actors and authority, UC-001 request intake, and the distinction among command, decision, a locally recorded fact, and client acknowledgement. This lesson makes their identifiers and state ownership precise.

**Learning contract:** Distinguish OrderId, CustomerId, RestaurantId, PaymentAttemptId, request/correlation IDs, and external provider references; defend entity continuity, source of truth, versions, aliases, projection staleness, and cross-model ownership. Implement only justified typed domain IDs and create-only local state in the existing single deployable. No real merchant, payment, refund or durable infrastructure exists.

## Orient — The order that appeared paid without a payment

A customer receives a message saying **Payment completed**. The customer opens their order page and sees a matching green label. Yet a hypothetical provider receipt associated with the customer's transaction says **authorization only**; a second provider lookup says **capture not found**. Which representation should the support engineer believe? A common mistake is to debate whether the UI or the database is "correct" before asking **what business fact is in dispute, who can establish it, and which operation and entity each piece of evidence describes**.

Three quite different observations can all be present without logically contradicting one another. A platform can record an order request; a provider may have authorized a potential charge; a screen can display a stale combined status. Only the first is a fact supported by our current Java application. The latter two are conceptual examples for learning about future integrations. Neither a favorable UI color nor a 201 response to \`POST /api/orders\` establishes merchant acceptance or payment completion.

Think of identity as the answer to **which thing?** and state as the answer to **what is currently known about that thing?** A source of authority answers **who is entitled to establish the particular fact?** A timestamp answers a different question: **when did a given clock or component observe it?** When these questions are collapsed into a single status string, systems can look successful while losing the causal evidence required for operations and customer trust.

Our running example uses one order intake. A successful local \`PlaceOrderCommand\` produces a new \`OrderId\` and an immutable Order snapshot. The same application constructs \`OrderRequestRecorded\` only after its process-local repository's save returns normally. That fact remains narrow: it says the platform recorded a customer request in that process. It says nothing about a merchant's decision or a payment provider's operation.

The goal of this lesson is to build a model strong enough to answer a difficult question: **When an order has two related payment attempts, three HTTP retries and a stale status projection, which identifier do we use to reconstruct each history without falsely combining them?** A correct design can withstand that question before any microservices, payment adapter, database or event broker exists.

In Lesson 1.1.3 we learned that a command is not an established fact. Here we add a further constraint: **even a genuine fact can be misapplied if it is attached to the wrong identity or read from the wrong authority**. The rigorous solution is not automatically a new database or distributed messaging system. It is first a precise identity and authority contract, then the smallest implementation that preserves it.

### Orientation questions

Before reading further, write brief independent answers: Does a changed restaurant name create a new RestaurantId? Can the same OrderId have two PaymentAttemptIds? Does a repeated \`X-Request-ID\` guarantee an existing OrderId is reused? When a customer-facing status disagrees with a provider's operation receipt, which organization can prove capture? Do not assume an implemented payment integration in this application.

**Scope boundary:** The actual Java code currently knows order intake, a synthetic catalog, and process-local snapshots. Payment attempts, provider receipts, merchant decisions and multi-system aliases are deliberately hypothetical. The chapter will distinguish those sources every time.

## Understand — Identity, attributes, state, version and history are different dimensions

An **entity identity** distinguishes one continuing business thing from every other thing in its valid namespace. Two orders can contain the same customer, restaurant, basket and price yet still be distinct orders. One order can have changed state and still be the *same* order. Equality of attributes does not establish identity, and inequality of attributes does not necessarily destroy it.

An **attribute** describes a property: a restaurant's display name or an order line's synthetic price. A **state** is a configuration of relevant attributes and lifecycle claims at a particular point. A **state snapshot** captures those values for reading; the snapshot need not be a historical event, and it may become stale immediately. A **version or revision** expresses a particular entity-state revision under an enforced version protocol. A version is not the entity's identity. A **history** is evidence of how authoritative changes occurred, which may require immutable records and appropriate durable storage. Our current application does not offer such a history log.

The distinctions matter because operational instructions must be framed against the correct target. **Create order request** means establish a new entity if eligible; **retrieve order by ID** means return the existing entity or report absence. A future approved **change shipping instruction for OrderId X** would mean apply a guarded change to *that same entity*, not generate a new OrderId. The current backend has only creation and retrieval. It does not yet have that modification use case or a versioned write protocol.

### Worked example: stable identity, changing knowledge

Consider a conceptual order with identity \`OrderId = O-17\`. At time T1, the platform has recorded intake: status \`REQUESTED_AWAITING_RESTAURANT\`, restaurant decision \`PENDING\`, payment status \`NOT_STARTED\`. At T2, a future integrated restaurant might accept fulfillment. The same OrderId should still refer to that order; the state change must arise from authorized restaurant evidence rather than a UI toggling a field. At T3, a separate provider operation might be reported. The provider's own operation identity and evidence would be associated with the same order without replacing it.

A useful conceptual table is:

| Dimension | T1 | T2 (future, conceptual) |
|---|---|---|
| \`OrderId\` | \`O-17\` | \`O-17\` — stable |
| Order-related state | Intake recorded | Merchant acceptance confirmed by authorized merchant |
| Revision | No production version yet | Conceptual \`v2\` only if an actual version contract exists |
| Evidence | Local post-save fact | Merchant-authored acceptance evidence |
| Customer projection | Awaiting restaurant | Confirmed only after authorized observation |
| PaymentAttemptId | None | Independent if a payment attempt is later initiated |

Notice that a hypothetical revision number is not magically valid just because the example displays \`v2\`. A proper optimistic-concurrency mechanism must define expected revision, atomic compare-and-update, conflict behavior, and tests. Without those elements, a \`version\` field is decoration, not a correctness guarantee. Likewise, an \`Instant\` timestamp is not a globally increasing sequence; clocks can move backwards and distributed observations may arrive out of order.

### Identity continuity versus immutable snapshots

In our actual Java domain, \`Order\` is an immutable record. A read of a stored Order returns the snapshot associated with its stable identity within the running process. The repository—not the record's Java fields—owns the mutable collection mapping IDs to snapshots. Two distinct business concepts must therefore be kept separate: *the identity of the order* and *the mutable map that stores references to immutable Order values*.

The new Lesson 1.1.4 repository uses atomic \`putIfAbsent\` for creation. Once an OrderId exists, another \`save\` with that same identity fails instead of overwriting it. This is an intentionally narrow invariant. It establishes create-only local ownership, not a general update pathway, payment-state transition or durable audit trail.

Why not write a convenient setter or new \`updateStatus()\` just to demonstrate versioning? Because doing so would invent business authority and transition guards that have not yet been validated. An unapproved status update teaches a false model. It is more valuable to recognize the architectural gap explicitly: **we know how to create an intake, but do not yet know which subsequent mutations are authorized**.

### Invariants to defend

The same business entity must retain its ID under every legitimate future update. Creating an unrelated business entity must use a different ID even when payloads match. A request ID must not silently become an entity ID. An immutable snapshot must not be presented as proof of an immutable historical audit. A displayed status must not claim a state the underlying authoritative owner has not established.

## Understand — The identity vocabulary: order, customer, restaurant, attempt and observation

A well-formed design names each identifier according to *what it identifies*. The string or UUID syntax alone tells us almost nothing about its meaning. An \`OrderId\` and \`CustomerId\` could both be UUIDs, but passing one in place of the other is a semantic error even when a programming language accepts the same underlying type.

### OrderId: identity of one intake resource

Our Java service generates \`OrderId\` only after the fixture request passes business checks and before constructing a new \`Order\`. The repository stores the resulting immutable snapshot under this identity. \`GET /api/orders/{id}\` looks up that existing resource and does not create another OrderId. This is a real implemented guarantee **within a running process**, not a restart-durable claim.

A second eligible \`POST /api/orders\`, even with identical customer and basket, currently creates a second intake with another OrderId. This is the expressly non-idempotent contract. Reusing a logical operation ID in a future deduplication design would require a separate approved key and protocol, not merely reusing the same request payload.

### CustomerId: a reference, not authentication

The existing HTTP payload includes a UUID in \`customerId\`. The platform currently accepts it as a claimed reference. The code has no authentication context establishing that the caller actually owns this customer. Type safety prevents swapping a CustomerId with an OrderId in domain code; it cannot prove user identity, permission or authenticity.

Never infer authorization from the mere presence of a syntactically valid identifier. Future authenticated customer identity and acting-on-behalf-of rules require a separate security contract.

### RestaurantId: stable catalog code, not a display name

The teaching catalog resolves \`cedar-kitchen\` as a restaurant code. Its display name can be "Cedar Kitchen (fictional demo)" without changing the code. Two real merchants might share a name, one company may own multiple restaurants, and an external marketplace may use different merchant reference namespaces. These possibilities do not justify fabricating a real multi-merchant integration today.

A restaurant's public name is useful for people. Its stable ID is useful for referential continuity. When a merchant changes branding, a lookup should not silently create a different business entity merely because a label changed. Correct identity mapping is a domain policy, not a string-equality heuristic.

### PaymentAttemptId: one attempt, not the order

Conceptually, one OrderId can relate to PaymentAttemptId P1 and P2. A failed attempt followed by a legitimate retry may create a new attempt without creating a new order. The attempted provider operation also has its own reference and exact external authority. A payment attempt is not necessarily a successful authorization, capture or settlement.

**This type is not implemented in the Java application.** Its proper future location depends on a validated payment workflow. The current design stops at the identity and authority map because no provider integration exists yet.

### Request, correlation, tracing and operation IDs

An HTTP request ID can distinguish an attempt to communicate. A correlation ID connects related observations across components. A trace ID typically identifies a trace of execution spans; neither is inherently a stable business-order ID. A provider transaction reference identifies an operation in a provider namespace, subject to that provider's contract. A proposed idempotency key would identify a logical operation *only when the server enforces* its scope, payload-consistency rules, retention period, conflict behavior and atomic reuse semantics.

These identities can form a relationship without being equal:

\`\`\`text
CustomerId C-1 ──initiates──> OrderId O-1
HTTP request R-1 ──attempts──> Create O-1
HTTP request R-2 ──later repeats intent──> Create O-2   [CURRENT NON-IDEMPOTENT BEHAVIOR]
OrderId O-1 ──conceptually relates──> PaymentAttemptId P-1 and P-2
Provider operation Q-7 ──references──> one specific PaymentAttemptId
Trace T-1 ──observes communication──> R-1
\`\`\`

Do not mistake the diagram's example labels for generated production data. The arrows establish the distinction in identity *types* and relationships. No real payment attempt exists.

### A practical classification rule

For any unfamiliar identifier, ask: **what exactly can I retrieve with it, in whose namespace, for how long, and what operation would create another one?** If the answer is "it makes logging easier" rather than "it identifies a business thing with an authority," the ID may be technical rather than domain identity. If one operation can produce multiple IDs of that kind, it is probably not the stable identity of the parent entity.

## Understand — Natural keys, surrogate keys, namespaces and aliases

A **natural key** uses a value with business meaning, such as a government registration number, a merchant's assigned reference or a restaurant catalog code. A **surrogate key** is generated primarily to provide stable identity independent of changing attributes. Neither is universally superior. The appropriate choice depends on uniqueness scope, mutability, exposure, trust and migration requirements.

The \`RestaurantId("cedar-kitchen")\` used by the current teaching catalog is a local code within one fixture namespace. It must not be confused with a globally unique, regulator-approved legal merchant identity. The \`OrderId(UUID)\` is an application-generated value used as the stable local order-intake key. Its UUID representation is convenient across API and tests, but it does not by itself guarantee authorization, durable existence or non-collision across all possible integrations.

**Namespace is part of identity interpretation.** Provider A's transaction reference \`123\` and Provider B's reference \`123\` need not refer to the same financial operation. A merchant's externally assigned partner ID should normally be interpreted together with its issuer/provider namespace. Similarly, two restaurants with the same display name cannot be merged without authoritative mapping evidence.

### A concrete aliasing trap

Suppose two restaurant catalog entries display "Cedar Kitchen." One represents Merchant M-17 in Addis Ababa; the other represents Merchant M-62 in another location. If a booking or order service joins records on the display name, it may attach a customer's request to the wrong merchant. A customer-visible name is neither a reliable natural key nor proof of a shared legal entity.

Aliases arise when names change, providers rename references, partners migrate between systems, or a business genuinely consolidates accounts. Identity mapping is not arbitrary string normalization. A legitimate alias link requires an authority, evidence, effective dates where relevant, and a policy for conflicts and reversals. Two identifiers might refer to one continuing entity, but that equivalence must be established—not guessed from similar spelling.

### Generated IDs and security misconceptions

UUID values reduce many practical collision risks but should not be treated as secrets or access-control capabilities. Guessability, collision probability, request authentication and permissions are different concerns. Do not infer that exposing a UUID in \`Location: /api/orders/{id}\` authorizes arbitrary reads; our teaching API currently has no user authorization layer. A production design must address that separately.

Changing a business key may require migration of references, foreign keys, caches, read models, operational dashboards and historical evidence. Surrogate IDs can simplify continuity across renamed external identifiers, but they also require careful mappings from the external authority to the internal stable reference. One cannot replace correctness with another table that silently assumes aliases are true.

### Choosing a representation

| Candidate | Advantage | Primary hazard |
|---|---|---|
| Raw UUID in every layer | Simple initial plumbing | Easy to swap semantically unrelated UUIDs |
| Typed \`OrderId(UUID)\` | Expresses invariant and prevents accidental type substitution | Requires deliberate HTTP/persistence adapters |
| Restaurant catalog code | Human-readable local fixture key | Namespace and rename policy may be unclear |
| Restaurant display name | Readable by users | Not stable/unique enough as authority |
| Provider reference | Tied to provider evidence | Must include provider/merchant scope, may arrive late |
| Correlation ID | Helps reconstruct communication | Not a business-operation uniqueness guarantee |

The present Java evolution adds \`OrderId\`, \`CustomerId\` and \`RestaurantId\` as immutable value types in the domain. It retains the same outward UUID and String shapes at the HTTP boundary. This avoids a broad breaking API change while making the internal meaning of business references explicit. PaymentAttemptId remains conceptual until there is a real payment model to anchor it.

## Understand — State revision, immutable history and the cost of pretending an update exists

A real business entity can persist over time while its snapshots change. That is why we need **stable identity** plus a *separately defined* state and version model. But our code today records only the first intake. There is no approved \`AcceptOrder\`, \`UpdateOrderStatus\`, \`CapturePayment\`, or \`CorrectOrder\` use case. This is not a deficiency to conceal: it is an honest design boundary established by the current roadmap sequence.

Imagine a future authorized restaurant decision that changes the order's fulfillment status from \`PENDING\` to \`ACCEPTED\`. A well-designed implementation would target an existing OrderId, check the restaurant actor's permission and applicable business guards, then commit a new state while retaining the same identity. It would also need an explicit policy about concurrent modifications and a reliable way to distinguish stale writes. **None of that is implemented now**, and creating a status-update method without those rules would make the learning project less correct, not more complete.

### Revision versus time versus event sequence

A state revision number is useful only if the state owner defines its meaning. Is the initial value zero or one? Does each successful change increment it exactly once? Can concurrent writers compare expected revisions atomically? Are failed attempts excluded? Must an external provider response cause a new local revision? How do clients detect conflicts? These are business and concurrency contract questions, not choices answered by adding a \`long version\` field.

An immutable historical fact is different from a mutable snapshot. \`OrderRequestRecorded\` in Lesson 1.1.3 states that one local save returned normally and records the relevant order, customer and restaurant IDs. It is constructed after the adapter returns. It is not itself durably stored in a separate event journal. The Order snapshot has \`createdAt\`; the fact has an \`observedAfterSaveAt\` observation timestamp. Those timestamps can help diagnose chronology, but they do not define a globally monotonic sequence or a transactional revision protocol. Wall clocks may be corrected or observations delayed.

Consider two hypothetical state writers. Both read Order O17 at revision 4; each proposes a different legal change. If both later write without an atomic conditional update, the last write can overwrite the other. Merely stamping revision 5 on each candidate does not prevent lost updates. A database compare-and-swap update or properly scoped concurrency mechanism would be needed when actual updates are introduced. The current in-memory \`ConcurrentHashMap\` only offers local atomic operations for the behaviors we explicitly implement.

### The narrow but genuine Lesson 1.1.4 improvement

The repository now stores a typed \`OrderId\` key and performs \`putIfAbsent\` when creating an intake. This guarantees, within a single running application process, that **one exact ID cannot silently replace an existing Order snapshot**. Two concurrent creates attempting the same ID cannot both overwrite the entry. One succeeds and the other reports an error. That is a real local correctness property backed by a concurrent unit test.

It does *not* guarantee that two identical HTTP requests use the same ID. Our server creates a fresh OrderId for each eligible invocation; both can succeed under separate keys. It also does not guarantee crash durability, globally unique IDs across arbitrary sources, authenticated ownership, or that a future legal state transition is automatically guarded.

The result is a clean separation between today and tomorrow: a stable Order identity and create-only state ownership are implemented; update/version semantics are documented as future design obligations. **A version counter should follow a real business transition contract, not precede it.**

## Understand — Authority is a business contract, not a database location

A source of authority is the actor or system entitled to make a particular business assertion under an agreed contract. An observer can receive, store or display an assertion without becoming the authority that created it. A projection can derive a convenient representation from multiple observed facts, and a cache can repeat that representation quickly. None of those steps transfers ownership of the underlying business result.

This is most obvious in a marketplace. The platform can assert that it received and locally recorded a customer's request. The restaurant would be entitled to decide whether it accepts fulfillment under its policy. A payment provider is the authority for its actual financial operations under its contract. A carrier may be authoritative for a delivery scan it performed. These facts are connected in a customer journey but belong to different decision rights and different kinds of evidence.

The currently implemented Food Ordering Platform does not call the restaurant, payment provider or carrier. Its synthetic menu catalog provides fixture data so the application can reject unknown or unavailable demo items. A successful fixture lookup is *not* a restaurant's real-time authorization to prepare food. The API's fields \`restaurantDecision: PENDING\` and \`paymentStatus: NOT_STARTED\` deliberately reveal those missing external facts instead of producing a falsely optimistic status.

### Four layers of information about one fact

**Authority:** Who can legitimately establish the fact? For example, the provider operating the money movement can say what its authenticated operation actually accomplished.

**Observation:** What did our platform receive or query? A provider callback might announce that an operation changed. Observation must identify the exact provider, account and operation to which the claim applies.

**Projection:** How do we translate observed facts into a read-friendly local view? A customer portal may combine order intake, merchant approval and payment state into an order-progress label. Projection freshness, provenance and unknown values matter.

**Presentation:** What text or color does the customer actually see? The UI is a delivery mechanism, not the source of financial truth. Showing a green "Paid" badge is not an accounting event.

These layers can disagree because an observation is delayed, a projection is stale, an identifier was joined incorrectly, an external source corrected an earlier claim, or the UI applies an invalid derivation. Investigating a disagreement requires recovering identity and causality, not simply declaring the newest timestamp authoritative.

### A derived order-status trap

Suppose a conceptual future dashboard displays one \`OrderStatus = PAID\`. Was the provider authorized, captured, settled or merely asked to start an operation? Does \`PAID\` mean payment succeeded while the restaurant still rejected? Could a refund have been requested after capture? Is it a client-only optimistic display? A single overloaded status variable loses critical distinctions.

An honest projection might instead show separate sourced dimensions: **Order request recorded**, **Restaurant decision pending**, **Payment not initiated**. If a provider integration is later added, it should distinguish each attempt and each operation's authoritative result; an unknown or delayed result must not be silently converted into success or failure. Customer-friendly language can summarize this state, but the underlying facts must remain inspectable.

### Authority matrix

| Proposition | Entitled authority | Platform role today |
|---|---|---|
| Customer submitted an HTTP request | Client intent, observed by platform | Record an unverified claimed customer reference |
| Order intake was recorded locally | This running Spring Boot application's repository/handler | **Implemented** after normal save return |
| Restaurant accepted the order | Authorized restaurant/merchant | **Not implemented; PENDING** |
| Card payment was authorized | Actual provider under its financial contract | **Not implemented; NOT_STARTED** |
| Payment was captured | Actual capturing provider/ledger | **Not implemented; cannot assert** |
| Refund completed | Authorized provider/accounting evidence | **Not implemented; cannot assert** |
| UI status was refreshed | UI/read-model system | May assert refresh time, not the external effect |

The word *authority* here describes a business/evidence contract, not a requirement for separate microservices. An eventual modular single deployable could still store multiple concepts while carefully distinguishing externally owned facts. Architecture must follow validated business responsibilities and quality-attribute forces.

## Explore — One OrderId, multiple payment-attempt identities

Imagine an approved future payment flow for one order O-17. The customer tries to pay. Attempt P-101 times out before the platform receives a response. The customer tries again; another legitimate attempt P-102 is created under the same order. The provider's internal operation references are different again. Which ID answers the support team's question?

\`\`\`text
OrderId O-17  (one customer-visible order)
   ├── PaymentAttemptId P-101 (conceptual)
   │      └── Provider operation ProviderA/OP-501  [outcome unknown]
   └── PaymentAttemptId P-102 (conceptual)
          └── Provider operation ProviderA/OP-509  [authorized, not necessarily captured]
\`\`\`

O-17 identifies the parent order. P-101 and P-102 identify distinct execution attempts. ProviderA/OP-501 and ProviderA/OP-509 identify provider operations within Provider A's own namespace. An \`X-Request-ID\` may identify each HTTP invocation that initiated them, and a trace ID may connect the journey across processes. These values should be related, not mechanically copied into one another.

A crucial failure occurs if support searches by OrderId alone, sees *one* successful attempt and concludes the *whole* order is paid. The older attempt might still be unknown; another provider operation could later settle unexpectedly. The correct diagnostic question is not "What is the order's status?" in isolation. It is **Which payment attempt and which provider operation does this receipt describe, and what exact financial stage is proven?**

### Why retry is not a synonym for duplicate

A repeated HTTP message can represent the same logical operation whose reply was lost. It can also represent a deliberate second attempt after a known failure. A callback can be redelivered because its acknowledgement was lost, while the provider operation itself occurred only once. A business user can legitimately create a second order with the same basket. These cases require different idempotency, identity and authority rules.

The current application has no \`PaymentAttemptId\` implementation, no provider callback handler, and no safe-retry contract for \`PlaceOrder\`. Thus our diagram is a **conceptual future relationship**, not an executed Java trace. Its teaching purpose is to make identifier scope visible before business operations are added.

If a future provider returns "authorized," do not promote that to "captured" or "settled." Authority is fact-specific. The provider may be authoritative for all three kinds of operation in its environment, yet those words describe different financial effects. A correctly typed operation reference does not authorize inventing a more advanced state.

### Model boundary: internal references are not foreign microservices

A PaymentAttemptId is conceptually a separate entity identity, but a separate entity need not live in a separate deployable. Order and payment models can be distinct within one application and still have carefully defined references and owners. We do not introduce a Payment microservice merely because a second ID appears in a diagram.

The staff-level rule is: **separate identity and authority first; separate deployment only when measurable scaling, isolation, ownership or operational forces justify it**. This lesson teaches the former and defers the latter.

## Explore — Restaurant aliases, repeated callbacks and incorrect identity joins

Two restaurants called "Cedar Kitchen" might be completely unrelated merchants. A chain may have two branches sharing a brand but different fulfillment capacity. A legal merchant may expose distinct partner IDs in different marketplaces. A display name therefore cannot be an authoritative identity join key unless a specific registry guarantees the relevant uniqueness and continuity.

Consider a conceptual marketplace integration:

| Field | Restaurant A | Restaurant B |
|---|---|---|
| Display name | Cedar Kitchen | Cedar Kitchen |
| Internal RestaurantId | R-17 | R-62 |
| External merchant reference | PartnerX/M-07 | PartnerX/M-28 |
| Fulfillment decision | Accept | Reject |

If the platform groups both rows using the common name, the customer might see acceptance from Merchant A on an order targeted at Merchant B. The UI output can look self-consistent while describing the wrong entity. Reconciliation requires the authoritative mapping for the exact namespace and source, not a guess based on text.

### Repeated callbacks: identity of observation versus identity of effect

A hypothetical provider sends callback C-71 reporting Operation OP-501. Due to a network retry, the same callback is delivered twice. The platform observes C-71 on two HTTP deliveries. Did the provider charge twice? **No conclusion follows from the delivery count alone.** The business effect is identified by the authenticated provider operation and its actual financial statement, not by the number of messages received.

Now suppose the provider sends an updated report C-72 for OP-501. That may be a new observation about the same operation rather than a second operation. Or a new callback could refer to OP-509, which *is* a distinct attempt. Without namespace and operation identity, a consumer can create phantom charges or accidentally suppress legitimate outcomes.

The correct future ingestion contract would address authentication, issuer namespace, event/callback identity, provider operation identity, replay behavior, ordering rules, signature validation, data freshness and conflict resolution. It might later require durable deduplication or reconciliation. **None of that provider-integration code is implemented in this lesson.**

### Three ways a status can be wrong

First, a projection may lag despite accurately correlating identifiers: the provider's operation is captured but the UI still shows pending. Second, the projection can be current but joined to the wrong merchant or attempt: a recent successful event for another operation contaminates the order. Third, the platform may have received only an ambiguous acknowledgement: the UI claims completion without a definitive provider fact. Fixes differ: refresh/reconcile the projection, repair identity mapping, or recover authoritative provider evidence.

A production diagnosis must preserve ambiguity until evidence distinguishes these mechanisms. Updating the database's status field to match what support expects is not an investigation and may erase the clues required to correct the cause.

## Predict — Identity changes that should and should not create new entities

The purpose of this exercise is not to click through a set of definitions. It is to predict the identity, authority and customer-visible consequence of a concrete change before the model explains it. We will use one deterministic **Identity & Authority Explorer** located beside this explanation in the React textbook.

For each scenario, answer four questions in writing before running the model: **Which entity exists? Which ID remains stable? Who can establish the disputed fact? What is still unproven?**

### Scenario A: Restaurant rename

Restaurant R-17 changes its display name from "Cedar Kitchen" to "Cedar Table" under a valid authorized rename policy. The entity's identity remains R-17; only its name attribute changes. The present Java fixture does not implement a rename command. The example is conceptual: it teaches continuity, not a real executed state change.

### Scenario B: Two payment attempts

Order O-17 has conceptual payment attempts P-101 and P-102. One attempt's provider operation is unknown; another reports authorization. The OrderId must remain O-17; the attempts have distinct IDs. "Payment completed" cannot follow from authorization alone.

### Scenario C: Same-name merchants

Two restaurants share the display name "Cedar Kitchen" but have different merchant identities. Merging them based on display name creates an aliasing error. A correct result keeps their RestaurantIds distinct unless the proper authority explicitly approves a real identity-merge mapping.

### Scenario D: Redelivered provider callback

A provider callback for one operation is delivered twice. There may be two observations of one message or two delivery attempts, not two charges. The platform must correlate to the same provider operation identity and handle repeat delivery according to a tested contract before asserting any new financial effect.

### Scenario E: A stale "Paid" projection

The customer screen displays "Paid"; the latest verified provider evidence only confirms authorization, and capture is unknown. This is a projection/authority conflict. The safe interpretation reports what is known and what remains unsettled; the UI must not upgrade it to capture because its own display has become green.

### Scenario F: An accidental second create under an existing ID

The developer constructs a new Order snapshot reusing OrderId O-17 with a different quoted total and tries to save it as another intake. Our Java repository's create-only behavior rejects overwriting the existing entry. It does not create a valid state revision. A *legitimate* future update would require an approved command, guards, atomic revision handling and authorization, rather than calling create again.

### Scenario G: Identical PlaceOrder POST twice

The current system treats two eligible POST executions as two creates and generates two different OrderIds. That is different from Scenario F. Neither identity is silently overwritten, but the platform **still does not provide idempotency**. The remedy for accidental duplicate intent would require a separately designed and enforced operation identity.

After completing the lab, attempt to articulate a single general rule: **new entity identity is justified by the semantics of a new business entity, not by a changed attribute, a new HTTP delivery or an unreliable projection**. The exercise intentionally contains both implemented and conceptual cases; always look at the label identifying which is which.
